## Findings

F1. The 3a evidence that "last-bit differences do not matter" is vacuous; my own test finds the claim holds within the bars at 900 s and 1800 s but not as a blanket statement, and the "exact stream" bar has little headroom at 3600 s.
Severity: MAJOR   Confidence: HIGH   Lens: R3
Claim: In the 1e-15 perturbation runs the perturbation never reached any array (all typed arrays are byte-identical) and the "hashes changed, so it reached the solver" argument is a non sequitur, because the hash covers `stats.weather`, which echoes the perturbed input. When I inject real V8-versus-glibc-sized noise, burnt-status flips do occur (about half of the runs on a sensitive seed at 3600 s), so "(tested)" in the artifact and "expected difference about 0" in plan section 10 are overstated.
Evidence:
- I decoded frames with `r3_cmp.mjs`, base against `-pert1e-15`: fast 0/900/1800 s, fast seed 13, standard 1800 s, high-noembers 1800 s. In every pair, "arrays differing 0" of 25 typed arrays (191,720 to 408,224 elements). The only differing JSON leaves that are hashed: `snapshot.stats.weather.temperature` 31.400679617908942 -> 31.400679617908978, `stats.weather.windSpeed10` 9.357385577824623 -> 9.357385577824633, `stats.ffdi` 41.71143005414908 -> 41.711430054149176. `SimSnapshot.stats.weather: WeatherHour` is in `src/core/types.ts` (SimStats) and `snapshotHash` skips only `msPerSimMinute` and `engine`. At t=0 only 7 bytes differ, all in the JSON header. So 3a-tier-difference.md section 3 "(The snapshot hashes change ... so the perturbation reached the solver)" is wrong; the 1e-15 perturbation is absorbed by Float32 storage. The 1e-9 runs are real (spot-fire x, y differ at the 1e-9 level), but only two seeds, fast tier, and they are smooth input changes, not libm noise.
- I measured the actual disagreement, V8 12.4.254.21 (Node 22.22) against glibc 2.39 (what .NET calls on Linux x64), 400,000 random inputs per function: exp 9.67 % of calls differ, log 0.86 %, sin 3.31 %, cos 3.31 %, tan 3.83 %, atan 1.44 %, cbrt 47.78 % (up to 3 ulp), pow 9.80 %, atan2 17.63 %, sqrt 0 %; all others at most 1 ulp. One fast-tier 1800 s run makes about 3.7 M such calls (exp 1.73 M, atan 565 K, cos 502 K, log 278 K, sin 218 K, hypot 186 K, cbrt 160 K, atan2 127 K).
- I then injected noise with those probabilities (R3_REAL=1) into the TypeScript solver and compared with the same seed, same tier, same machine (differ = % of ever-burning cells that burn in only one run):
  - fast seeds 12 to 16, 1800 s, 2 noise seeds each (10 runs): 9 identical; 1 run (seed 13) 0.09 % differ, max 20.9 s.
  - fast seeds 12 to 16, 3600 s, 2 noise seeds (10 runs): noise seed 1 all identical; noise seed 2 changed arrivals in all 5 (1 to 1,282 cells, max 0.0002 s to 723 s), and seed 13 flipped burnt status: 0.56 % differ, area -0.46 %, max 723 s, p95 39.7 s.
  - fast seed 13, 3600 s, noise seeds 1 to 10: burnt status flipped in 6 of 10 (differ 0.05, 0.05, 0.05, 0.46, 0.56, 0.56 %; area -0.05 to -0.46 %; max 128 to 723 s; p95 1.5 to 40 s). The outcomes repeat (the same alternative fire shows up under several noise seeds), so these are discrete ember-landing bifurcations, not smooth noise.
  - uniform worst case (every call off by 1 ulp), seeds 12, 14, 15, 16 at 1800 s: seed 14 0.41 % differ, max 49 s; the others 0. Seed 13 at 3600 s with the same noise: 0.51 and 0.60 % differ (two noise seeds), max 350 s, p95 34 to 41 s.
  - standard tier seed 13, 3 noise seeds (50 % of calls nudged), 1800 s: 0 / 0 / 277 cells changed, max 1.8 s.
- The exporter caps at the scenario duration: `--to 7200` returned the 3600 s result, so I could not go longer.
Why it matters: The bars are only checked at 900 s and 1800 s. At 3600 s a correct, exact-stream port already differs by up to 0.56 % of cells from the libm difference alone (the tight column allows 1 %), and the effect grows with time; the app's scenarios are 3 to 6 h. A correct port could fail the tight bar at longer horizons and the report would blame the random stream. The owner also reads "tested" as settled.
Plan change: (1) Replace the 1e-15 evidence with the noise-injection study above (run it with the 30 seeds, three tiers, 900/1800/3600/10800 s; scripts are in `r3-tools/`). (2) Set the Stage 3 bars as a multiple of the measured noise floor at each horizon, add 3600 s and 10800 s checkpoints, and report the first snapshot at which the ember set differs, so that stream divergence is told apart from libm noise. (3) Reword the artifact: "last-bit noise changes the result in a minority of runs by under 1 % of cells at 1 h".
Already covered?: Partly: section 10 admits the risk is the stream, and the bars have slack at 1800 s. It does not cover the invalid evidence, the discrete flips, or horizons beyond 1800 s.

F2. "Identical on 1, 2, 4, 8 threads" and "TypeScript random stream and draw order ported exactly" cannot both hold for the biggest fast-tier module, so Gate 1 (a kernel) can pass while the solver as a whole stays serial.
Severity: MAJOR   Confidence: HIGH on the code, MEDIUM on the speed-up bound   Lens: R3
Claim: Ember transport draws from one mulberry32 stream in particle order, inside variable-length sub-step loops; the spread step draws from a second stream inside the level-set band loop via a callback; and cell preparation is order-dependent within a pass. Exact draw order therefore forces these parts to run on one thread, and a `Parallel.For` kernel benchmark does not measure the serial remainder.
Evidence:
- `src/embers/EmberModel.ts:673-674` `while (i < this.count) { if (this.advance(i, ...)) this.removeAt(i, this.goneAt); else i++; }`, with `removeAt` (line 2203) moving the last particle into slot i; `advance` (1367) copies the stream state `let rs = rr.s` (1458) and draws inline (1602-1654: `rs = (rs + 0x6d2b79f5) >>> 0; ...`) for `su > 0`, `sw > 0`, re-flame; the number of sub-steps per particle depends on the wind it samples. Emission: `const np = this.r.poisson(...)` then `spawn` (lines 629-630), same `this.r`.
- `src/fire/spread/levelSet.ts:269-275` (`hooks.ensureSpeed(k)` inside the `evaluate` band loop) -> `FireSpreadModel.ts:479` -> `prepareCell` (1379) -> `breachDraw` -> `this.rng.next() < p` (1504); debris ignitions draw at 1981. `prepareCell` writes shared scratch (`const s = this.prep`, line 1382).
- `computeCell` (1284): `if (first) e0 = this.maxNbr(k, this.pE)` (line 1353) reads neighbours' `pE`, which `prepareCell` writes (1418) in the same pass, so a parallel or reordered pass gives different numbers (a Gauss-Seidel dependency, not a pure kernel).
- `src/sim/simulation.ts:434-437` has four independent streams (embers seed, fire seed+1, explain +2, atmosphere +3), so embers and fire are independent of each other but each is sequential internally.
- `src/sim/simulation.ts:1182-1190`: tier `auto` "reads the wall clock ... the tier never changes": with more threads, `auto` picks a different tier, so "results never depend on speed" (plan rule 4) is false for `auto` by design.
- TypeScript profile on Katoomba 6 km, 1800 s (K1's scratch files `scratchpad/dotnet-build/prof-fast.json`, `prof-standard.json`, Node 22, shared 4 cores): fast tier embers 25.6 %, fireStep 14.1 %, fireHeat 12.3 %, snapshot 11.6 %, atmosphere 0.3 %; standard tier atmosphere 67.5 %, embers 8.9 %, surfaceWind 7.4 %. K1's in-progress log (another worktree, not final) reports 7.28x all-core for a kernel that is in the atmosphere module, which is 0.3 % of the fast tier.
- Inference: with embers (25.6 %) serial the whole fast-tier step is capped at 1/(0.256 + 0.744/n) = 2.2x at n=4 and 2.7x at n=8 over single-thread C#, before the other serial parts above.
Why it matters: The phone is the stage 1 target and likely runs the fast tier. A Gate 1 pass on the atmosphere kernel says nothing about it. Either the ember step is single-threaded (then say so), or the stream changes to per-particle streams (then the tight column of the bars no longer applies and the owner gets the loose 12 % ensemble bar). The plan states both.
Plan change: In 3b add a serial inventory (each module marked RNG-sequential, order-dependent, or data-parallel, with its share of the TypeScript profile above). Restate rule 4 as "bit-identical across thread counts with the tier pinned explicitly; RNG-sequential modules are single-threaded by design" or pick counter-based streams now. Make Gate 1 a whole-step benchmark (fast tier 1800 s, 1 and all cores) with the Amdahl bound written next to it.
Already covered?: Rule 4 and section 10's "Decision taken for stage 3" each address half; the conflict and the gate's blind spot are not mentioned.

F3. "JavaScript gives the same results on every device" is stale: since V8 15 (Chrome 150, July 2026; inference on the version mapping) V8 uses LLVM libc, Node 22 (the fixture reference) uses fdlibm, and the plan never compares C# with C# across operating systems.
Severity: MAJOR   Confidence: HIGH (facts), MEDIUM (consequences)   Lens: R3
Claim: Within one V8 version JavaScript math is the same everywhere; across versions it is not, and a current Android System WebView (Chrome 157 stable since 2026-11-03; the owner's phone version is not known) differs in the last bit from the Node 22 host and from every stored fixture. For C#, Microsoft documents that `Math.*` results may differ by operating system and architecture. The plan tests C# on one Linux x64 container only; stage 4 on the phone compares nothing numerically.
Evidence:
- V8 `src/base/ieee754.cc` at tag 12.4.254.21 (Node 22.22.0 reports `12.4.254.21-node.33`): about 3,000 lines of fdlibm, with `libm_sin`/`libm_cos` -> `glibc_sin` only `#if defined(V8_USE_LIBM_TRIG_FUNCTIONS) && defined(BUILDING_V8_BASE_SHARED)`. At 15.3.9 (365 lines) and `main` (245 lines, fetched 2026-11-12) every function is a wrapper, e.g. `double exp(double x) { return LIBC_NAMESPACE::shared::exp(x); }`, `double sin(...)`, `cos`, `log`, `atan2`, `cbrt`, `legacy::pow`, with `#include "third_party/llvm-libc/src/shared/math.h"`. At 15.0.99 log, sin, cos, tan, cbrt already forward. chromiumdash: Chrome 150 early-stable 2026-07-15, Chrome 157 stable 2026-11-03, Chrome 158 stable 2026-11-17. V8 15.y shipping in Chrome 15y is V8's version numbering (inference from the 14.0 = Chrome 140 pattern; I did not look up a Chrome-to-V8 table), so today's WebView is V8 15.7.
- ECMA-262 section 21.3.2 (tc39.es, fetched 2026-11-12): "The behaviour of the functions acos ... exp ... hypot ... pow ... sin ... is not precisely specified here ... some latitude is allowed ... an implementer should be able to use the same mathematical library for ECMAScript on a given hardware platform that is available to C programmers on that platform."
- Learn `Math.Sin` (net-11.0 default moniker, updated 2026-10-16): "This method calls into the underlying C runtime, and the exact result or valid input range may differ between different operating systems or architectures."
- Android bionic `libm/Android.bp` on main (fetched 2026-11-12): `whole_static_libs: ["libarm-optimized-routines-math"]` plus FreeBSD `s_sin.c`, `s_cos.c`, `s_atan.c`; glibc uses other algorithms for sin, cos, atan, so a phone, a Linux desktop and a Windows host will not agree bit for bit (inference for the Windows UCRT; not looked up). The 1 to 48 % per-function mismatch above is the size of the effect between two libms.
- `src/ui/desktopRestart.ts:3-4`: "The two engines cannot hand a running state to each other, so it is a restart, and it says so." So "Continue on this device" needs no state handover (a plus), but a restarted run on the phone already shows the same fire only to within F1's differences today (Node 22 host against WebView V8 15.x), and would again with C#.
- I found no test in the repository that compares the Node engine with the in-browser engine: `desktop/engine.test.ts:139-170` compares two Node-hosted controllers; the e2e hash code (`e2e/robustness.spec.ts:360`) compares the browser with itself.
Why it matters: The premise behind "keep TypeScript for consistency" and the artifact's "same solver, same stored hashes" is weaker than stated, and a desktop-versus-phone replay difference exists today. Without a cross-platform C# check the owner cannot know whether a Windows host and an Android phone show the same fire.
Plan change: (1) Add a free control before any porting: run the same fixtures in current Chromium (V8 15.x) and compare with Node 22 under the bars; the bars must pass that, or they are too tight. (2) From the first line of Fs.Kernel route every `exp`, `log`, `pow`, `sin`, `cos`, `tan`, `atan`, `atan2`, `cbrt`, `hypot` through one static `FsMath` class, so a managed shared implementation (for example a CORE-MATH port, as community packages offer) can replace the platform libm if cross-platform identity becomes a requirement. (3) In stage 4 add a numeric check: the same fixture through the phone's C# engine, the container's C# engine and the phone's WebView TypeScript, compared with the F1 bars. (4) Fix the artifact sentence on A to say "same results to within last-bit noise on a given V8 version".
Already covered?: No. Section 3 and 10 say bit-identical hashes with TypeScript are "not the bar" but say nothing about C# against C# across platforms.

F5. The plan's JavaScript-versus-C# checklist is three items; at least six more bite in this code, two of them silently.
Severity: MINOR   Confidence: HIGH (sites), MEDIUM (impact)   Lens: R3
Claim: (a) JS `Map` keeps insertion order and `delete` then `set` moves a key to the end; .NET `Dictionary` does not promise order after removals. (b) V8's sort is stable; `Array.Sort` and `List.Sort` are not. (c) JS typed-array `sort()` puts NaN last; `Array.Sort(float[])` puts NaN first. (d) `Math.round` rounds half up; `Math.Round(double)` rounds half to even. (e) about 110 uses of the NaN idiom `!(a > b)` in non-test solver files (regex count over fire, embers, atmosphere, sim, core, fuel, terrain) and about 40 of `x === x`. (f) ECMA-262 `**`/`Math.pow` returns NaN for `1 ** NaN` and `(+-1) ** +-Infinity`, IEEE and .NET give 1. (g) `float * float` in C# is float arithmetic. (h) the string sort in `explain/engine.ts:202` is ordinal in JS and culture-sensitive by default in C#.
Evidence:
- (a) `src/sim/simulation.ts:1668` `byId.delete(e.id); // a later record ... replaces it and goes to the end` then `[...byId.values()]` feeds `windOverrideFrom`.
- (b) `src/atmosphere/base.ts:1002-1003` `idx.sort((a, b) => g.zs[a]! - g.zs[b]!)` then `idx[idx.length >> 1]` (median column, ties broken by index order only if the sort is stable). Learn `Array.Sort` (net-11.0): "This implementation performs an unstable sort".
- (c) `src/terrain/analysis.ts:865-866`, `src/atmosphere/grid.ts:353`, `src/fire/terrainFeatures.ts:476` take quantiles from typed-array sorts.
- (d) 86 `Math.round` sites in the solver, e.g. `terrainFeatures.ts:426,455`, `FireSpreadModel.ts:686` with crest sector 22.5 degrees (a tie at 11.25 + 22.5k degrees). Learn `Math.Round(Double)`: "rounds midpoint values to the nearest even number". I checked the real grid mappings (fire cells to air columns, `atmosphere/grid.ts:316-318`) for standard, high and high30: 0 exact ties in 200 to 300 cells, so it is not triggered there.
- (e) the idiom in `levelSet.ts:234,489,542` (`!(p > 0)` makes NaN count as burnt); an automatic "simplify" to `p <= 0` flips NaN behaviour.
- (f) ECMA-262 6.1.6.1.3 Number::exponentiate (fetched 2026-11-12) "differs from IEEE 754-2019".
- Float to integer: `(int)x` saturates and maps NaN to 0 on .NET 9+ (Learn, updated 2026-09-14); JS `x | 0` wraps for |x| >= 2^31 and gives 0 for NaN, so only huge values differ (not seen on solver paths); .NET 11 CoreCLR also saturates `(byte)`, `(short)` (Learn 2026-11-10) where a JS `Uint8Array` store wraps.
Why it matters: Each is a systematic difference far larger than libm noise, and the agreement bars may pass or fail on them by accident.
Plan change: Add a "port conventions" list to 3b (`Math.Floor(x + 0.5)` for `Math.round`; no `Dictionary` iteration for order; a stable sort or an explicit tie-break; NaN-last sort helper; `double` locals when reading `float[]`; `string.CompareOrdinal`; never invert a negated comparison) and a test per item (ties, NaN, removal-then-insert) before any comparison against fixtures.
Already covered?: Section 3 lists float storage with double arithmetic, no FMA, fixed-order reductions; not these.

## Checked and found sound
- Random generator: `Rng.next` / `FastRng.next` (mulberry32, `src/core/rng.ts`, `src/embers/sampling.ts`) port exactly with `uint` wrapping arithmetic; `Math.imul`, `>>> 0` and `t ^= t + imul(...)` are all low-32-bit operations. Port details to keep: `seed >>> 0 || 0x9e3779b9` (seed 0 and NaN map to the constant), the `spare` Box-Muller cache that is cleared at each public call, the 4,096-entry normal table built with `Math.log` at load (tiny last-bit effect).
- The level-set core (`levelSet.ts`) has no transcendental calls (0 `Math.exp/log/pow/sin/cos` hits) and no `Map`, `Set`, `sort` besides a numeric typed-array sort; its arithmetic is `+ - * /` and `sqrt`, exact on both runtimes. libm enters through `computeCell` and `math.ts`, the ember model and the atmosphere.
- Date and `Intl`: the solver path uses UTC arithmetic only (`simulation.ts:1501`, `moisture/model.ts:754`); `scenario/time.ts` (Intl time zones) is imported only by `sim/testing/scenarios.ts` in the closure.
- The 1e-9 perturbation runs did propagate (spot-fire coordinates differ at about 1e-9), so that part of 3a is real evidence of a linear response; only the 1e-15 runs are vacuous.
- 3a determinism across processes (31 hashes identical) holds, and my `P=0` harness reproduced a fixture byte for byte.
- Plan section 3 already commits to double arithmetic with Float32 storage, no FMA contraction, and fixed-order reductions; I did not find a primary source on whether RyuJIT contracts `a*b+c` (see below), so that check must be run, not assumed.
- .NET 11 on Android is CoreCLR only (`UseMonoRuntime` removed in Preview 6, NETSDK1242; via secondary search results quoting the .NET blog of 2026-05-13), so the Mono conversion differences in the Learn notes do not apply to the MAUI target.
