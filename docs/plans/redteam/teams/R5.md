F1. The phone gates are specified for Debug APKs, which are not representative for speed
Severity: BLOCKER   Confidence: MEDIUM   Lens: R5
Claim: Plan section 5 says the benchmark and transport APKs are "debug builds". In .NET 11 MAUI a Debug Android build is "CoreCLR + JIT" with no ReadyToRun, and Debug also compiles unoptimised, so a Gate 1 phone number ("under 2.0x the TypeScript: stop") or a Gate 2 transport rate measured on it can fail on build configuration, not on architecture.
Evidence: plan line 76 "Install the benchmark and transport APKs (debug builds, sideload)"; the toolchain agent's own check is `dotnet build -f net11.0-android -c Debug` (`scratchpad/android-t2/doctor-build.sh`). Microsoft Learn, "Runtimes and compilation in .NET MAUI" (ms.date 2026-10-08, updated 2026-10-13), net-maui-11.0 table: "Android | CoreCLR + JIT | CoreCLR + composite partial ReadyToRun + JIT", and "For Android apps, ReadyToRun is enabled by default in the Release configuration." Learn "Publish an Android app using the command line" (ms.date 2026-10-08): "AndroidKeyStore ... default value is false" and the build-properties page says false means "the default debug-signing key will be used", so a Release APK installs by adb without any custom keystore; there is no signing reason to use Debug. BenchmarkDotNet refuses non-optimised assemblies (secondary sources only: project README via search), which is why section 9 is fine on the desktop; nothing protects the phone app. The size of the Debug penalty on this kernel is my inference, not measured.
Why it matters: Section 7 says "Gate 1 fails: No speed argument for B anywhere. Stop." A Debug-built benchmark app can produce that verdict falsely and end the project, or make a transport look slower than it is.
Plan change: In section 5 and the K1/T2/I4 briefs, every APK whose numbers feed Gate 1, 2, 4 or 5 is built `-c Release` (`-p:AndroidPackageFormats=apk`, not debuggable, R2R defaults left on). Debug builds are for functional smoke only. Add the build configuration, `Optimize` and R2R state to rule 3 and to the results header. If a Release APK cannot be built, label the phone number "Debug, indicative, not a gate" and do not apply Gates 1 and 2 to it.
Already covered?: no. Section 9 applies BenchmarkDotNet to the desktop only; section 5 asks for debug.

Claim: (a) Saved sites and runs are lost to a MAUI page by construction (different origin), so "test what survives" is a known answer; (b) an install over the current APK is only possible with the same applicationId, the same signing certificate and a higher versionCode, none of which the plan states, and the current signing key exists only in this container; (c) the existing page depends on three Capacitor-bridge features that do not exist in a MAUI WebView, so stage 4's "so the page needs no change" is false.
Evidence:

- Signing: `apksigner verify --print-certs` on `firesim-0.6.0-debug.apk` and `firesim-0.8.0-debug.apk`: both "CN=Android Debug", SHA-256 `f7570f27329a8569200885b4666781e7ce564b8201369cbae0904fa2b7a862e7`, v2 only. A throwaway key in a reclaimable container is a poor long-term identity for either shell.
- Bridge: `src/ui/prefs.ts:4-9` uses `@capacitor/preferences` (SharedPreferences, "survive WebView storage eviction") and falls back to localStorage when `Capacitor.isNativePlatform()` is false; `src/data/http.ts:4-14,111` uses `CapacitorHttp` natively and, in a browser, calls CORS-enabled services directly but says "the one service without CORS headers (the Meta canopy-height bucket) is routed through the dev-server proxy"; `src/ui/location.ts:35,80` uses `@capacitor/geolocation`. F3. No rule or gate keeps the ASP.NET Core host as hard as the Node host; defaults are weaker exactly where the Node host is strict
Severity: MAJOR   Confidence: HIGH   Lens: R5
Claim: The plan's rules (section 1) contain no "host security must not get weaker" rule. The committed `Fs.Host` is the `dotnet new web` template (`Program.cs`: `MapGet("/", () => "Hello World!")`; `appsettings.json`: `"AllowedHosts": "*"`), ASP.NET Core's WebSocket middleware allows every Origin by default, and stage 4 reuses only three Playwright specs, which exercise a minority of the Node host's guards.
Evidence: Microsoft Learn, "WebSockets support in ASP.NET Core" (updated 2026-11-11): "AllowedOrigins - ... By default, all origins are allowed"; `KeepAliveTimeout` "default is Timeout.InfiniteTimeSpan (disabled)"; KeepAliveInterval default two minutes; the page itself says "Applications should be configured to validate these headers". Node host: `desktop/server.test.ts` has 65 cases and `desktop/security.test.ts` 23; the e2e specs the plan names are `desktop-real.spec.ts` (7 tests), `desktop-cross-origin.spec.ts` (3) and `host-browser.spec.ts` (9: hostile name, CORS, one-use `--open` link). Guards with a Vitest test and no e2e test: 5 s hello timeout; 4 pre-hello connections per address and 16 in all (503); close 1008 for more than 20 pings or 1000 messages a second or 64 MiB queued for 10 s; 1009 above 128 MiB; 4503; text frame after welcome; the decoder limits (8 MiB header, 4096 arrays, arrays that share bytes, `__proto__`) and the per-session memory estimate refusal (`desktop/README.md` "The engine link" items 4 and 7). The e2e specs also start the Node CLI (`--lan`, `--allow-app`, `--allow-host`, `--open`), so the C# host must implement the same flags to be tested at all.
Why it matters: The owner would approve "Node host retired" (artifact) on a stage 4 pass that never tested the hello timeout, the connection caps, the message-rate close, the frame limit or the memory refusal. The decoder limits are inside the engine slice, which stage 3b to 3e define without mentioning them.
Plan change: Add rule 7 "host parity: every refusal the Node host makes (status, close code, limit) is made by the C# host". Stage 4 gate: a protocol-level conformance suite, run against both hosts over a socket, derived from `server.test.ts`, `security.test.ts` and `openToken.test.ts`, plus the three Playwright specs. Put the decoder's hostile-input limits and a memory bound (`GCHeapHardLimit` or an estimate like `sessionEstimate.ts`) into the stage 3 slice. Set `AllowedHosts`, `WebSocketOptions.AllowedOrigins`, `KeepAliveTimeout` and Kestrel limits explicitly in `Program.cs`; do not ship the template defaults.
Already covered?: partly. Section 3 stage 4 names the specs; it names nothing of the other guards and states no parity rule.

F4. Protocol 2 over an in-app loopback socket is the wrong shape: the secret cannot be typed, and every local app is "one address"
Severity: MAJOR   Confidence: MEDIUM   Lens: R5
Claim: Stage 2(c) and stage 4 reuse protocol 2 unchanged on 127.0.0.1 and plan only to "measure and write up" exposure. Exposure is already documented, and three properties of protocol 2 break on loopback: (i) its secret is an 8-character code a person types or reads from a URL fragment; (ii) its abuse limits are keyed by remote address; (iii) the port is not secret.
Evidence: localmess.github.io (Local Mess, 2025; USENIX Security 2026 paper): "any installed app with the INTERNET permission to open a listening socket on the loopback interface (127.0.0.1)", browsers on the same device reach it "without user consent or platform mediation", and localhost is exempt from mixed-content rules. `desktop/security.ts` `addressKey` and `RateLimiter`; `server.test.ts:153` "after 5 wrong codes from one address that address is refused with 4429, even with the right code, for 60 s"; `server.test.ts:621` "16 silent connections from one address take 4 slots". On loopback the page and every other app are `127.0.0.1`: another app can send 5 wrong hellos (60 s lockout, repeatable) or hold 4 silent sockets and starve the page of its own engine. A fixed port can be bound before FireSim starts (fake fire pictures in a training app). ASP.NET Core accepts any Origin by default (F3 quote). `desktop/README.md` "The pairing code": the page picks the code up from the address or asks the person to type it, which an in-app page cannot do; injecting it through interop is a page change, a constant is no secret. `network_security_config.xml` today is `base-config cleartextTrafficPermitted="true"` for every host and `capacitor.config.ts` sets `allowMixedContent: true` for the whole WebView; for loopback neither should be needed, so a loopback-only link can run with cleartext limited to localhost/127.0.0.1 and no mixed-content switch (inference, to be tested on the phone). dotnet/maui `HybridWebViewHandler.Android.cs` comment: JS to .NET "flow through the SendMessagePath HTTP endpoint ... (gated by HasExpectedHeaders), not AddJavascriptInterface", i.e. routes (a) and (b) open no listening socket.
Why it matters: A "measured" exposure with no pass criterion would let stage 2(c) win on throughput while being an unauthenticated service to every app on the phone, or one that a co-resident app can switch off.
Plan change: Stage 2(c) counts as passed only if it (1) listens on an ephemeral 127.0.0.1 port chosen per launch and handed to the page by interop; (2) uses a per-launch 128-bit secret delivered by interop, never typed; (3) keys the lockout and pre-hello caps by connection or secret, not address; (4) requires Origin equal to the shell's origin; (5) runs with a loopback-only network security config and no `allowMixedContent`; (6) survives a co-resident-app test (a second test APK that connects without the secret, then floods) with the page still served. If it fails any, (a) or (b) is the transport and (c) stays a desktop-host-only idea. Record this as the stage 4 exposure result instead of "measured".
Already covered?: no. Section 3 stage 4 says only "measured and written up, against the interop route".

F5. Nothing pins or tests targetSdk, and the default for this SDK is Android 17, which gates local networks
Severity: MAJOR   Confidence: MEDIUM   Lens: R5
Claim: The plan lists only the API floor (24). The installed .NET 11 Android workload ships one reference pack, API 37, so a template `net11.0-android` app targets 37, while the current app targets 36. Android 17 blocks local-network traffic by default for apps targeting 37, and stage 4's only network test (airplane mode) cannot see it.
Evidence: `scratchpad/dotnet-sdk/packs/`: only `Microsoft.Android.Ref.37` (37.2.31); `WorkloadDependencies.json` requires `platforms;android-37.0` (non-optional); the template csproj has `<TargetFrameworks>net11.0-android</TargetFrameworks>` and `SupportedOSPlatformVersion` 24.0. `android/variables.gradle`: `targetSdkVersion = 36`. developer.android.com/privacy-and-security/local-network-permission (read 2026-11-12): "local network protections are enforced for apps targeting Android 17 or higher"; "Making an outgoing TCP connection | yes"; "Traffic originating from Android Webviews that require local network access will inherit permission state from the host app"; "TCP connections will typically result in a timeout error"; "If your app targets SDK 36 or lower, local network access is implicitly granted using the INTERNET permission." The page does not say whether 127.0.0.1 counts. Chromium blink-dev (via search, secondary): Local Network Access for WebSockets is "unsupported on WebView", where the permission is "unconditionally granted"; so the app-level permission is the only gate. Play: support.google.com/googleplay/android-developer/answer/11926878 (read 2026-11-12): new apps and updates from August 31, 2026 must target API 36 or higher.
Why it matters: The opt-in Wi-Fi desktop link (0.9.0) would fail as a timeout in a MAUI build at target 37 with no permission prompt in the plan, and the loopback link's status under Android 17 is undocumented. Both are found only on an Android 17 phone, which the plan does not ask for ("Say which phone and Android version" is the only prompt).
Plan change: Add to stage 4 and 5: record `targetSdkVersion` in every result header; build at 36 and 37; on an Android 17 device test the loopback link and the Wi-Fi desktop link at target 37 without and with `ACCESS_LOCAL_NETWORK` (the 2027 Play API-37 step will force this later). Pin the target in `AndroidManifest.xml` (`<uses-sdk android:targetSdkVersion="36">`) for the Android 16 comparison. Ask the owner now for the phone's Android version, since the answer decides whether this can be tested. For store readiness add to stage 5: `zipalign -c -P 16 -v 4 app.apk` and a 16 KB-page device or emulator run. developer.android.com/guide/practices/page-sizes (read 2026-11-12): "If your app only uses code written in the Java programming language or in Kotlin ... then your app already supports 16 KB devices" (today's Capacitor app); Option B adds `libcoreclr.so`, `libclrjit.so`, `libmonodroid.so`, `libassembly-store.so` (Learn runtimes page, APK contents), and "Starting February 1, 2027, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates." Partial local evidence: `libnet-android.release.so` and `libarchive-dso-stub.so` from the CoreCLR Android pack have LOAD alignment 0x4000; the runtime libraries themselves are not on disk (the pack install failed, F7), so unverified.
Already covered?: no. Stage 5 lists "Android 7.0 (API 24) floor" only. (The floor itself is right, see "Checked".)

F6. Stage 4 has no background, process-death or sustained-load test, and protocol 2 will likely drop the link after a background
Severity: MAJOR   Confidence: MEDIUM   Lens: R5
Claim: The only lifecycle check is a 10-minute foreground run in airplane mode. Android freezes cached apps; protocol 2 closes a silent link after 60 s and has no reconnect. With the engine behind that link, a phone that is backgrounded for more than about 70 s probably returns to a closed link and a lost run, where today's in-page worker simply resumes. Gate 1 is a short burst, so it also cannot show sustained all-core throttling.
Evidence: source.android.com/docs/core/perf/cached-apps-freezer (via search; official page): "App processes in the cached state are frozen 10 seconds after entering the cached state"; unfreeze when importance rises; exemption by making the process non-cached (a foreground service). `desktop/README.md` "The engine link" item 4: "closes a connection that has been silent for 60 s"; "What is not here": "a reconnect after a lost link (the session goes with its worker)". That a frozen process's pings stop is inference from the freezer page ("suspends all its threads" is not stated there); how the C# host would time the 60 s is my assumption. Thermal: developer.android.com/games/optimize/adpf/thermal (via search): "Once the device overheats, the workload must drop below the sustainable performance level". Today's solver is one worker thread; the plan's C# is "all-core" on 4 to 8 cores of a phone.
Why it matters: A trainee who locks the screen mid-run loses the run in design B and not in today's app, and no gate would have said so. A 1.5x or 2.0x burst speed-up can disappear after minutes on a phone.
Plan change: Add to stage 4: (a) home-button and screen-off for 30 s, 90 s and 5 min, then return, recording link, run and who resumes; if the link dies, the design needs a protocol change (pause/resume or reconnect), which also falsifies "the page needs no change" (F2); decide whether a foreground service is acceptable (Play foreground-service type review, `docs/research/09-mobile-tech-stack.md` lines 225-227); (b) a 30-minute sustained run at 60x logging `PowerManager.getCurrentThermalStatus()` and picture cadence, repeated for the TypeScript worker on the same phone; (c) kill the process (`adb shell am kill`) and record what the person sees on relaunch.
Already covered?: partly. Section 3 stage 4 has "no crash, picture cadence held, memory within a stated budget" for 10 minutes in the foreground.

## Checked and found sound
- SDK download integrity: `sha512sum` of `dotnet-dl/sdk.tar.gz` equals `sdk-hash.txt` and the 11.0.100 entry in the downloaded `releases.json` (channel 11.0, released 2026-11-10, STS, eol 2028-11-14). So the plan's "official tarball, SHA-512 checked" is true (it is integrity from the same host, not an independent signature).
- API floor: Microsoft's breaking-change page (via search, learn.microsoft.com/dotnet/core/compatibility/maui/11/android-minimum-api-level) says .NET 11 moved the floor from 21 to 24; the template has `SupportedOSPlatformVersion` 24; the app's `minSdkVersion = 24`. Matches.
- The current app's target API 36 meets the Play requirement for August 31, 2026 (Play page above); the extension runs to November 1, 2026.
- WebView debugging: HybridWebView and BlazorWebView call `SetWebContentsDebuggingEnabled` only under `DeveloperTools.Enabled`, which the templates enable under `#if DEBUG` (Learn HybridWebView page, lines for `AddHybridWebViewDeveloperTools`); Capacitor's default is the same (`capacitor.config.ts` comment). Parity, no new exposure in release.
- JS interop surface: HybridWebView does not use `AddJavascriptInterface`; no CVE found for HybridWebView or BlazorWebView (searches 2026-11-12); the 2026 CVEs found are in Chromium/Android System WebView, which every option shares.
- Auto Backup: `android:allowBackup="true"` in both the current manifest and the MAUI template; Auto Backup is capped at 25 MB per app (developer.android.com/identity/data/autobackup), so the app's multi-megabyte IndexedDB data is unlikely to be backed up in either shell. No difference between A, B and today.
- The Node host's existing hardening is real and tested (Host 421, Origin 403, one-use link, 5-wrong-code limiter, caps): it is the right reference for F3.
- Fixtures and toolchain are kept out of git (`.gitignore`), and the plan's rule never to run downloaded install scripts is followed (`dotnet-try/dotnet-install.sh` was downloaded and not run).
- Chromium's Local Network Access prompt is, per blink-dev threads seen through search (secondary), unsupported in WebView, so a page-level prompt is not the risk; the app-level Android 17 permission is (F5).
