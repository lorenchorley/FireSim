## Findings

F1. Gate 1 passes at a level the repo already judged "not worth starting", and its comparator lets thread count pass for language speed
Severity: MAJOR   Confidence: HIGH (internal contradiction, quoted)   Lens: R6
Claim: The Gate 1 pass bars (all-core C# at least 1.5x TypeScript on desktop, 2.0x on the phone, plan section 3 row 1) sit at or below the 2 to 2.6x that plan 15e and D39 already judged not worth starting for speed, and because the TypeScript side is one thread, a C# kernel at language parity (1.0x) that scales 1.6x on four cores passes.
Evidence: plan section 3 row 1: "All-core C# is under 1.5× the TypeScript on desktop, or under 2.0× on the phone". 15e, Measured: "Amdahl upper bounds on 4 cores: the air alone 1.9x (Standard) and 2.6x (High); the fire alone 1.8 to 2.0x; about 3x only if the fire, the coupling and the embers were all split" and "Threads, WebAssembly and WebGPU are not worth starting for speed on this evidence (they would help the 3-D air by at most about 2 to 2.6x on 4 cores)". D39 (`air-slice-wind-detail-honest-speed.md`, line 126) repeats it. Stage 1 detail ports the kernel as scalar, `Vector<T>` and `Parallel.For`, "against the TypeScript in Node", with no TypeScript-with-threads arm. D34's note (15e update 2026-11-07) says the open speed options are "more cores in JavaScript (3), WebAssembly for a hot loop (4) and WebGPU (5)". README: the one measured phone ran the 3-D step in 41 ms against a limit of about 198 ms, "4.8 times that".
Why it matters: Gate 1 can pass while the owner's own earlier rule says "no", and a pass is then read as "there is a speed argument for B" when the cheaper options (Node or WebView worker threads, WASM SIMD) were never put against it. The owner would be spending the stage 3 port on a speed case that was never compared with the alternatives it competes with.
Plan change: In Gate 1 report three numbers on the same kernel and data: (1) C# one thread against TypeScript one thread (the language factor); (2) C# scaling from 1 to N threads; (3) TypeScript on the same fixed partition using `worker_threads` (about half a day for one kernel). Make the pass condition a projected whole-solver speed-up (kernel speed-up fed through the profile fractions, Amdahl) of at least 3x against the best TypeScript arm on the same machine, and say in section 7 that a pass below that "does not favour B over JavaScript threads". The 3x figure is a proposal for the owner; it is the 15e bound for splitting everything.
Already covered?: No. Section 7 row 1 handles only a fail; the bars are not reconciled with 15e.

F3. The prototype measures the fast tier, which is the odd tier out and not the default on a phone that can run the 3-D air; a pass on it would be read as "B is feasible"
Severity: MAJOR   Confidence: HIGH (quotes), MEDIUM (consequence)   Lens: R6
Claim: Stage 1 profiles "the Katoomba 6 km fast-tier scenario", and stage 3b allows the slice to feed the TypeScript's own wind rasters and defer the atmosphere, so all gates can pass without any C# 3-D air, which is 63 to 82 % of CPU in the tiers a capable phone uses.

Already covered?: Partly: 3b says "the report then says so", but section 7's wording does not carry the limit.

F4. Cross-platform determinism of the C# solver is untested, and the 1e-15 result cannot show insensitivity because the output is float32
Severity: MAJOR   Confidence: MEDIUM   Lens: R6
Claim: .NET's `Math.Exp/Pow/Sin/Cos/Log` call the platform C runtime and may differ between operating systems and architectures, whereas V8 uses its own fdlibm port, so "same seed, same result" between the ARM64 phone, the x64 desktop host and CI is untested; and 3a's "no float32 arrival value moved" at 1e-15 is guaranteed by float32 resolution, not evidence of insensitivity.
Evidence: Microsoft Learn, `Math.Exp` (net-11.0 view, page updated 2026-10-16): "This method calls into the underlying C runtime, and the exact result or valid input range may differ between different operating systems or architectures." Chromium `third_party/fdlibm/README.chromium` (tag 113, 2023): "may be useful when mathematical consistency across OS platforms is desired" (V8's use of it is from a secondary summary; I did not read V8 source). A Firefox jit-test (`fdlibm-for-pow.js`, search summary only, secondary) records that `std::pow` "returned a 1-ULP-different result on some Android ARM devices". 3a section 3: at 1e-15 "0 in every case"; at 1e-9 the largest change was 0.0006 s (seed 13) and 0.0012 s (seed 14). Arithmetic: float32 spacing near 1,000 s is 2^-14 = 6.1e-5 s, so any change below about 3e-5 s is invisible; 0.0012 s over an arrival of up to 1,800 s is about 7e-7 relative for a 1e-9 input, an amplification of about 600 to 1,200 in 30 minutes. Plan section 3 Stage 3 "Also checked" lists Float32 storage, no FMA contraction and fixed-order reductions, not libm. README promises determinism (V18).
Why it matters: If the C# hashes differ between phone and CI, the new baseline (which section 3 says "needs a new baseline") is per platform, `desktopDetail.determinism`-style tests cannot be pinned for the phone, and "Continue on this device" or a phone viewing a desktop host would show different fires for the same seed. This is discovered after the port, not before.
Plan change: Add to stage 3: (1) a libm micro-test: the same 1e6 inputs for exp, pow, sin, cos, log, atan2 through V8, .NET x64 and .NET arm64, with a histogram of ulp disagreements (cost: an hour); (2) a platform pair: the same C# build on linux-x64 and linux-arm64 (qemu-user if available in the container, else the phone APK in stage 4) on `katoomba3-fast` and seed 13, comparing all 31 hashes; (3) if they differ, either vendor a managed fdlibm port for the hot functions or write in the report that B ends cross-device reproducibility; (4) redo the perturbation test on an unquantized field (float64 arrival, or the hash of the unrounded state) at 1e-9 and 1e-7 and over a 4 h run.
Already covered?: No. Section 10 item 1 dismisses last-bit math on the 3a evidence.

F5. Stage 0's gate does not test the thing most likely to kill the phone stages (an installable MAUI Android APK), and "debug builds, sideload" runs into Fast Deployment
Severity: MAJOR   Confidence: MEDIUM   Lens: R6
Claim: Stage 0 stops only if "SDK cannot be installed"; whether a MAUI Android APK can be built here, and installed by hand without `adb`, is first met in stage 2 (T2), after K1 and P3a have spent; and section 5 specifies "debug builds, sideload", whereas a Debug build defaults to Fast Deployment, which relies on files pushed by tooling and has been reported to abort at launch with "No assemblies found" (the cure is a build property the plan does not mention).
Evidence: plan section 3 row 0; section 2 ("No `adb`, no Android SDK, no `dotnet`", "KVM / emulator: Not checked"); `ls /dev/kvm` in this container: "No such file or directory"; section 5: "The MAUI Android build in this container is not guaranteed" and "Install the benchmark and transport APKs (debug builds, sideload)". Learn, .NET for Android build properties (updated 2026-10-03), `EmbedAssembliesIntoApk`: "This property should be `True` for Release builds and `False` for Debug builds. It *may* need to be `True` in Debug builds if Fast Deployment doesn't support the target device." Learn XA0127 (updated 2026-09-24): "disable Fast Deployment by setting `EmbedAssembliesIntoApk = True`". dotnet/android issue #10708 (opened 2026-01-21): launch error "No assemblies found in '/data/user/0/.../files/.__override__/x86_64'". Positive evidence the plan can use: Learn installation page (ms.date 2026-06-15) lists "Linux | Android" as a supported target and `dotnet workload install maui-android`; `dl.google.com` and the Microsoft OpenJDK link answer 200 through the proxy (my `curl -I`, 2026-11-12); and `scripts/build-android-apk.sh` already builds a Capacitor APK in this kind of container. The owner's route today is download-and-install (README "Try it on an Android phone"), so "the owner builds" (section 5 fallback) assumes a toolchain nothing says they have (inference).
Why it matters: If the first MAUI build fails or the APK will not launch, K1's phone half, T2 and I4 (three of the six stages) cannot run, and that is learned after two agents' spend; the fallback pushes a MAUI toolchain onto the owner.
Plan change: Put into the stage 0 gate: `dotnet new maui-blazor` and `dotnet new maui`, `dotnet build -f net11.0-android -c Release` (and the Debug variant with `-p:EmbedAssembliesIntoApk=true`), the APK signed with the debug key as `scripts/build-android-apk.sh` does, `aapt2 dump badging` clean, size recorded, and a stop at failure the same as "SDK cannot be installed". State in section 5 that every sideloaded APK is Release-signed or Debug with embedded assemblies.
Already covered?: Partly: section 5 admits the build is "not guaranteed" and gives a fallback; neither moves the test to stage 0 nor fixes the Debug default.

F7. Gate 3 agrees at 30 minutes on one 3 km scenario; users run 1 to 12 hours, and the model's own results split hard over hours
Severity: MAJOR   Confidence: HIGH (facts), MEDIUM (consequence)   Lens: R6
Claim: The stage 3 bars are evaluated at 900 s and 1,800 s on one site, one start time and 630 to 1,700 burnt cells; the app's validation scenarios and its Auto policy are hours long, and 15e shows run results diverging by large factors over hours, so a pass at 30 minutes says little about a 6 h port.
Evidence: plan section 10 bars: "(same tier, same seed, 900 s and 1800 s)". 3a caveats: "One scenario, one site, one start time, 630 to 1700 burnt cells". Why it matters: A port that is exact for half an hour can still diverge once a spot-fire decision flips at hour 2; the owner would learn this in the full port, after the prototype said "faithful".
Plan change: Add to Gate 3 a 4 h Katoomba 6 km run with the south-west change (the 15e V20 preset; TypeScript fast tier about 5.3 s per simulated hour, so about 21 s) at seeds 12 and 13, and one run on a second site (Warrumbungles), compared at 1, 2 and 4 h. Report the time of first divergence of the burning set or an ember decision per seed as a number, not only end-state bars; if exact-RNG C# diverges before 2 h, the tight column of the bars cannot be claimed.
Already covered?: No. Section 10 "Still to run" lists 30-seed ensembles and quiet-machine timings, not long runs.

F8. Gate 2 measures the transports with an idle CPU and at a rate sized to today's TypeScript, which is not the condition B creates
Severity: MAJOR   Confidence: MEDIUM (rates derived), LOW (contention is inference)   Lens: R6
Claim: Stage 2 sends synthetic buffers with no solver load, at 4 pictures per second (2.2 MB) and 1 per second (16 MB); B adds an all-core solver running next to the WebView's render thread and, if Gate 1 passes, 2x or more pictures per second than the bars assume; and the transports tested exclude the no-base64, no-socket route.
Evidence: plan Stage 2 detail ("Synthetic buffers at the real sizes", "dropped frames of a running Three.js scene", no solver load named). The host coalesces to "at most ~25 per wall second" (`src/sim/host.ts` header; `src/sim/params.ts:109` `snapshotMinWallMs: 40`); today's worker transfers buffers (`src/sim/worker.ts`: "Snapshot arrays are transferred"). 15e: fast tier, 6 km, 30 m: 679x real time; with a 60 s picture interval and `snap-60.bin` of 2,283,808 bytes (3a) that is about 11 pictures per wall second on one desktop core, so the bar's 4 per second is about today's phone rate, not a faster one (derivation, inference for the phone). Microsoft HybridWebView source (`HybridWebViewHandler.cs`, main, fetched 2026-11-12): a comment says JS-to-.NET messages "flow through the SendMessagePath HTTP endpoint", and `SendRawMessage` takes a string. Learn "What's new in .NET 10" (via search summary) says BlazorWebView and HybridWebView can intercept web requests with `WebResourceRequested` and return local responses: a `fetch()` of a virtual URL served from .NET needs no base64 and no socket. Android documents that accepting an incoming TCP connection needs ACCESS_LOCAL_NETWORK for apps targeting SDK 37, and that "Traffic originating from Android Webviews that require local network access will inherit permission state from the host app"; it does not say whether 127.0.0.1 counts (developer.android.com, undated page, fetched 2026-11-12).
Why it matters: A transport can pass idle and stutter when the solver holds every core, which is how stage 4 would discover it at the end; and a bar sized to the old solver rate can pass while the faster solver's pictures cannot be carried.
Plan change: Run each transport while a `Parallel.For` busy loop holds N and N-1 cores, report tasks over 50 ms and Three.js frame times; set the rate bars to (TypeScript pictures per second on that phone) x (Gate 1 ratio), capped at 25 per second; add a fourth transport, a pull-based `fetch()` served through `WebResourceRequested`, which also removes stage 4's loopback-exposure question; add a build targeting SDK 37 to see whether the in-app Kestrel socket needs ACCESS_LOCAL_NETWORK.
Already covered?: Partly: section 3 stage 4 measures cadence over 10 minutes at 60x, which is slow (the speed range is 0.25x to 3600x) and comes after Gate 2.

## Findings 9 and 10 (over the cap of eight; the brief asked for ten)

F9. B cannot keep the Capacitor origin, so saved sites and runs cannot follow without a release of the current app
Severity: MAJOR   Confidence: MEDIUM   Lens: R6
Claim: A page hosted by MAUI's HybridWebView is served from `https://0.0.0.1/`, a constant the app cannot change; IndexedDB and localStorage are per origin, so the current app's saved data under `https://localhost` is invisible to it even if the files survive an install-over. That makes a data export from the Capacitor app a precondition of B, and the plan tests it last and without a gate.
Evidence: dotnet/maui `HybridWebViewHandler.cs` (main, fetched 2026-11-12): `private static readonly string AppHostAddress = "0.0.0.1";` and `AppOrigin` built as `{AppHostScheme}://{AppHostAddress}/` (scheme `https` on Android). `capacitor.config.ts`: "The scheme above must stay https (it is the page's origin and the key of every saved site and run)". Plan stage 5: "A MAUI shell serves from a different origin." I did not read BlazorWebView's Android constant (a secondary search summary says 0.0.0.0).
Why it matters: Existing users (and the owner's own sites and runs) lose their data on upgrade unless a Capacitor-era release first exports it; that is a separate release and a user step, found after the whole prototype.
Plan change: Move the origin test into stage 2's hello APK (install over the Capacitor debug APK with the same application id and key; open the page; list what storage is visible), and add to section 7 "All pass" the line "needs a prior Capacitor release that exports saved data".
Already covered?: Partly: stage 5 tests it, but last and informational, and the answer is predictable from the source.

F10. Under B the TypeScript solver does not retire, so the two-solver cost D34 avoided returns
Severity: MAJOR   Confidence: MEDIUM   Lens: R6
Claim: The artifact says choose B "only if you are ready to retire the TypeScript solver", but the browser/PWA path, the Playwright suite and the in-thread and demo engines all run the TypeScript worker, and a .NET process exists only in the MAUI shell and the ASP.NET host; the plan has no stage or decision line for what runs in a browser without a host.
Evidence: artifact (B figure): "same C# solver, Node host retired", "solver moved out". 15e: "The app already runs in a desktop browser and as a PWA". `e2e/` is 20,739 lines run against the web app. Plan 15 section 16 (D10 question): the in-thread engine fallback (140.6 kB) and demo engine (15.0 kB) are kept by default ("default: no" to dropping them). Plan section 7 says only that "D34 would then be reopened".
Why it matters: Either the TypeScript solver stays (two solvers permanently, plus a parity suite), or the browser/PWA and offline-in-browser paths are dropped, or a .NET WebAssembly solver (single thread, per the artifact) is built; none is in scope or measured.
Plan change: Add to section 7 a required owner decision before any port: what runs in a browser with no .NET process, with the three options above and their costs; make it part of the "All pass" row.
Already covered?: No.

- The random generator is cheap to port exactly: `src/core/rng.ts` and `FastRng` in `src/embers/sampling.ts` are mulberry32 on uint32 with `Math.imul`, and the uniform draws are integer-exact; only `normal()`, `logNormal()` and `poisson()` use libm.

- The Stage 2 baseline is stated correctly: the worker transfers snapshot buffers (`src/sim/worker.ts` `transfer: true`), and the host coalesces cadence snapshots to at most about 25 per wall second.
- The mixed-content part of transport (c) has precedent: the shipped app already opens `ws://` from `https://localhost` with `allowMixedContent: true` and a cleartext rule (`capacitor.config.ts`).
- Section 1 rule 4 and the thread-count requirement are coherent with the fixed-partition design and the single sequential ember stream; the plan names "reductions in a fixed order".
- 3a determinism check (31 hashes identical across three Node processes, regression anchor equal) is internally consistent with its own report; I did not re-run it.
