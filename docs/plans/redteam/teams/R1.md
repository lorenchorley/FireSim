# Red team R1 (PLATFORM) report, 2026-11-12

Scope: are the platform claims in `docs/plans/dotnet-option-b-prototype.md` and the artifact true, and can the prototype be built and run as planned. Seven findings, ordered by effect on the owner's decision. Local checks were small (grep, `readelf`, one `df`) and only read files that already existed in the scratchpad (the dotnet SDK, the NuGet cache and the logs left by agent T2); nothing in the repository was touched.

---

F1. Stage 2 tests the wrong three transports: two are base64-on-the-main-thread by construction, and the two real binary routes are missing, so Gate 2 can fail falsely.
Severity: BLOCKER   Confidence: HIGH (facts), MEDIUM (consequence)   Lens: R1
Claim: Routes (a) BlazorWebView JS interop and (b) HybridWebView raw messages both carry a `byte[]` as a base64/JSON string through `WebView.PostWebMessage(new WebMessage(string))` and decode it on the page's main thread. Stage 2's own bar ("at most 8 ms of main-thread time per picture", "no main-thread task over 50 ms") cannot be met for a 16 MB picture by that path. Two documented routes that avoid base64 are not in the plan: (d) interception of an HTTPS request on the app origin, returning a `Stream` (HybridWebView and BlazorWebView `WebResourceRequested`), and (e) AndroidX WebKit's ArrayBuffer web message (`WebMessageCompat(byte[])`).
Evidence:
- Shipped MAUI 11.0.0 BlazorWebView page script, `.../microsoft.aspnetcore.components.webview/11.0.0/staticwebassets/blazor.webview.js` (in the T2 NuGet cache): `SendByteArrayToJS:jt` ... `function jt(t,n){const r=zt(n);e.dispatcher.receiveByteArray(t,r)}function zt(e){const t=atob(e),n=t.length,r=new Uint8Array(n);for(let e=0;e<n;e++)r[e]=t.charCodeAt(e);return r}` and `window.external.receiveMessage(e=>{ ... e.startsWith(Lt) ... JSON`. Command: `grep -o -E ".{120}atob.{160}" <that file>`. .NET side (raw.githubusercontent.com dotnet/aspnetcore main, read 2026-11-12): `IpcSender.SendByteArray` = `DispatchMessageWithErrorHandling(IpcCommon.Serialize(IpcCommon.OutgoingMessageType.SendByteArrayToJS, id, data))`, and `IpcCommon` ends in `JsonSerializer.Serialize(messageTypeAndArgs, ...)` (STJ writes `byte[]` as base64: inference, consistent with the `atob` above). dotnet/maui `AndroidWebKitWebViewManager`: `_webview.PostWebMessage(new WebMessage(message), AndroidAppOriginUri)`.
- HybridWebView on Android: dotnet/maui `MauiHybridWebView.SendRawMessage(string rawMessage) { PostWebMessage(new WebMessage(rawMessage), AndroidAppOriginUri); }` (main branch, read 2026-11-12). The shipped 11.0.0 `Microsoft.Maui.dll` (android37.0) contains `PostWebMessage`, `WebResourceRequested`, `TryInterceptResponseStream`, `AsyncStream` and no `WebMessageCompat` or `WebViewCompat` (python byte count over the dll).
- Route (d): Learn, HybridWebView page (ms.date 2026-07-08), "Intercept web requests": "handle the `WebResourceRequested` event ... set `Handled` to `true` and provide a response via `SetResponse(statusCode, statusDescription, contentType, streamOrTaskOfStream)`"; platform table: Android "Intercept HTTPS: yes, Intercept Custom Schemes: no". Shipped `Microsoft.AspNetCore.Components.WebView.Maui.dll` 11.0.0 also contains `WebResourceRequested` and `IWebRequestInterceptingWebView`. dotnet/maui `MauiHybridWebViewClient`: "Nothing in this file reads the full response into memory first" (stream goes straight into `WebResourceResponse`), which is how the framework itself serves `wwwroot`.
- Route (e): developer.android.com `WebViewFeature.WEB_MESSAGE_ARRAY_BUFFER` "Added in androidx.webkit 1.8.0 ... covers `WebMessagePortCompat#postMessage(WebMessageCompat)` with ArrayBuffer type, `WebViewCompat#postWebMessage(...)` with ArrayBuffer type"; `WebMessageCompat(byte[] arrayBuffer)` "Creates a WebMessage with JavaScript ArrayBuffer payload". `Xamarin.AndroidX.WebKit` 1.17.1 exists on NuGet (api.nuget.org flat container, 2026-11-12). The Capacitor app already pins androidxWebkitVersion 1.14.0 (`android/variables.gradle`).
- aspnetcore #35065 (opened 2021-08-05, closed 2025-09-05 as a duplicate of #62312) records that WebView transport has to "encode it as a string"; I found no dotnet/maui or aspnetcore issue about large payloads on Android either way, so I cannot say how slow (a) and (b) are, only that they cannot avoid the string path.
Why it matters: Section 3 gate 2 says "stop if no transport sustains the rates" and section 7 turns that into "B can only be a desktop-host design; a phone C# solver stops". With (c) not buildable as written (F2), the plan would measure only the two string routes, fail, and tell the owner that a phone C# solver is dead for a reason that is the plan's own choice of test routes. Inference on size: a 16 MB picture becomes about 21 MB of base64 inside a JSON string, then `atob` and a per-byte JavaScript loop on the main thread; that is very likely over 50 ms on a mid-range phone (not measured).
Plan change: Rewrite the Stage 2 list to five routes: (a) and (b) kept only as baselines expected to fail the 8 ms bar; (c) loopback WebSocket (see F2); (d) C# posts a tiny "picture N ready" message and the page does `fetch('/__pic/N').then(r => r.arrayBuffer())`, answered in `WebResourceRequested` with `SetResponse(200,"OK","application/octet-stream", Task<Stream>)` over the engine's own buffer; (e) a custom handler mapping calls `AndroidX.WebKit.WebViewCompat.PostWebMessage` or a `WebMessagePortCompat` with `new WebMessageCompat(bytes)`, guarded by `WebViewFeature.IsFeatureSupported(WEB_MESSAGE_ARRAY_BUFFER)`. Change Gate 2 to "stop only if none of the five sustains the rates", fix the section 7 row to match, and record main-thread milliseconds per route including the page's own decode, so the 8 ms bar is applied to the whole receive path.
Already covered?: No. Section 3 "Stage 2 detail" and section 7 list and rely on exactly (a), (b), (c).

F2. Transport (c) and Stage 4's "in-app Kestrel" cannot be built with supported means: ASP.NET Core has no runtime pack for Android.
Severity: MAJOR   Confidence: HIGH (no pack), MEDIUM (that no supported workaround other than not using Kestrel exists)   Lens: R1
Claim: `Microsoft.AspNetCore.App`, which holds Kestrel, is not available for `android-*` or `linux-bionic-*` runtime identifiers in .NET 11, so a MAUI Android project cannot reference it; the dotnet team's own tracking issue is still open in Backlog.
Evidence:
- The installed 11.0.100 SDK, `sdk/11.0.100/Microsoft.NETCoreSdk.BundledVersions.props`: for `net11.0`, `Microsoft.AspNetCore.App` `RuntimePackRuntimeIdentifiers="win-x64;win-x86;osx-x64;linux-musl-x64;linux-musl-arm64;linux-x64;linux-arm;linux-arm64;...;freebsd-arm64;linux-riscv64;..."` with no android or bionic entry, while `Microsoft.NETCore.App` lists `android-arm64;android-x64;android-arm;linux-bionic-*`. Reproduce with a short python regex over that file.
- api.nuget.org flat container, 2026-11-12: `microsoft.aspnetcore.app.runtime.android-arm64` and `microsoft.aspnetcore.app.runtime.linux-bionic-arm64` both return HTTP 404; `microsoft.aspnetcore.app.runtime.linux-arm64` returns 200.
- dotnet/aspnetcore #35077 "Support for MAUI runtimes in ASP.NET Core?": Open, milestone Backlog, opened 2021-08-03, latest comments 2025-12-19; Eilon (2021-08-05): hosting "requires platform support", not available on "some platforms, such as Android ... For right now I'm not aware of any plan to support this." No Microsoft statement for .NET 9, 10 or 11 in the thread. Microsoft Q&A (Rob Caplan, 2022-06-14) points to the same issue. Secondary: community posts report `NETSDK1082` "no runtime pack for Microsoft.AspNetCore.App ... android-arm64".
- The BCL does have what a hand-made server needs: `WebSocket.CreateFromStream(Stream, bool isServer, string subProtocol, TimeSpan keepAliveInterval)` in `System.Net.WebSockets.dll` (Learn, API page updated 2026-05-27, applies to net-11.0).
Why it matters: Stage 2 route (c) and the whole Stage 4 design ("C# engine ... speaking protocol 2 over loopback") are written as "in-app Kestrel". An agent will hit NETSDK1082 or ship unsupported copied assemblies. The desktop `Fs.Host` is unaffected (ASP.NET Core is supported on desktop).
Plan change: Replace "in-app Kestrel" in sections 3 and 4 with "`TcpListener` on 127.0.0.1, a hand-written HTTP/1.1 Upgrade handshake, then `WebSocket.CreateFromStream(stream, isServer: true, ...)`", and add to the T2 and I4 scopes a loopback test matrix that picks the narrowest configuration: (i) targetSdk 37 or above, where Android's Network Security Config doc says an implicit localhost configuration "Allows cleartext traffic" (localhost, ip6-localhost, or a numeric loopback IP); (ii) targetSdk 36, a `<domain-config cleartextTrafficPermitted="true"><domain>127.0.0.1</domain>` and nothing else; (iii) no `MixedContentMode` change, since the W3C Mixed Content algorithm step 1.2 allows a "potentially trustworthy URL" (spec read 2026-11-12; Android WebView's behaviour for `ws://127.0.0.1` from `https://0.0.0.1` is untested, so test it). The current app's `allowMixedContent: true` plus base-config cleartext for every host (`capacitor.config.ts`, `network_security_config.xml`) is the widest setting and exists for typed LAN addresses; do not copy it into the loopback prototype. Add to Stage 4: does Android 17's local-network permission apply to 127.0.0.1 (the docs are silent; a GrapheneOS thread says no, community only).
Already covered?: Partly. Section 3 Stage 4 says loopback exposure "is measured and written up", but it assumes the server exists and says nothing about how it is built or configured.

F3. Section 5 tells the owner to run phone benchmarks from debug builds, which Microsoft says gives unrealistic results; the Gate 1 phone threshold and every Stage 2 and 5 phone number would be biased against C#.
Severity: MAJOR   Confidence: HIGH (guidance), MEDIUM (size of the bias, not measured)   Lens: R1
Claim: A Debug .NET for Android build is the wrong artifact for the plan's phone gates (Gate 1: all-core C# under 2.0x the TypeScript; Stage 2 main-thread and GC numbers; Stage 5 size, start-up, memory).
Evidence: plan section 5 "Install the benchmark and transport APKs (debug builds, sideload)". Learn "Performance Profiling" (ms.date 2026-09-11, net-maui-11.0 view): "Always profile `Release` builds for accurate performance measurements." Learn "What's new in .NET MAUI for .NET 11" (ms.date 2026-09-10): "In `Release` builds, the runtime uses composite partial ReadyToRun by default. `Debug` builds don't enable ReadyToRun by default." The same page says Release CoreCLR builds trim and (for startup) use partial R2R, which a debug APK also lacks for size and start-up. The same guidance in the 8/9/10 view says debug uses the interpreter for hot reload "which significantly impacts performance and produces unrealistic results". My inference (standard .NET behaviour, not looked up here): an `Optimize=false` assembly is marked `DisableOptimizations`, so the JIT compiles it unoptimised. A debug APK is also far larger than a trimmed Release one, so the "against 33 MB" comparison would be meaningless.
Why it matters: Gate 1 on the phone is a stop gate. A debug-build run could fail it for a reason that has nothing to do with C# speed.
Plan change: Section 5 and the K1, T2 and R5 briefs: every phone number comes from `dotnet build -c Release -f net11.0-android -p:AndroidPackageFormat=apk` (sideload APK, signed with the debug keystore by default is an assumption to confirm), and the report states the configuration with each number; debug APKs are allowed only for "does it launch". Add the Release build's extra downloads (crossgen2 pack) to the disk budget in F4.
Already covered?: No.

The first `dotnet workload install maui-android` did succeed (`wl.log`: "Successfully installed workload(s) maui-android", EXIT 0), so the download route is real; the disk is the limit.

Change section 5 "all downloadable here" to "downloadable here; the container's disk blocked the one attempt".

F5. Stage 4 says the existing page runs in a MAUI shell "so the page needs no change"; the page depends on Capacitor's native bridge in at least four places.
Severity: MAJOR   Confidence: HIGH   Lens: R1
Claim: A MAUI shell has no Capacitor bridge, so `Capacitor.isNativePlatform()` is false and HTTP, location, preferences and the typed desktop address take their browser paths, which do not work there. The airplane-mode gate can pass while the features behind these fail.
Evidence (worktree `src/`): `data/http.ts:21,111,532` imports `CapacitorHttp` and returns `'native'` only if `Capacitor.isNativePlatform()`; its header comment: native HTTP is "not subject to CORS", and `useProxy()` sends the no-CORS service (`'chm'`, the canopy-height bucket, used by `data/canopy.ts:481`) to `${config.proxyBase}/proxy/chm/...`, a dev-server proxy that a MAUI shell does not have. `ui/mapsShortLink.ts` needs native HTTP with `disableRedirects` and otherwise refuses ("the plain web build cannot read the redirect"). `ui/location.ts:36,80` uses `@capacitor/geolocation`. `ui/prefs.ts:4,28` uses `@capacitor/preferences` because it "survive[s] WebView storage" clearing. `ui/desktop.ts:171` `const typed = Capacitor.isNativePlatform() || params.get('desktopaddr') === '1'` (typed LAN address UI), `main.ts:42`. `capacitor.config.ts` comments: `CapacitorHttp` routes `fetch()` "through the native HTTP stack so NSW government / BoM / Open-Meteo services work without CORS".
Why it matters: Section 7's "remaining cost" (the port plus Razor plus data migration) leaves out a native-services layer (HTTP, geolocation, durable preferences, files) that Capacitor supplies today, and Stage 5 "Can it replace the current APK?" will not surface it because it looks only at origin and size.
Plan change: Strike "so the page needs no change" in Stage 4. Add to Stage 4 a parity table with one row per Capacitor plugin the page uses (Http, Geolocation, Preferences, Filesystem, plus the `isNativePlatform()` branches), each with the MAUI replacement and whether the page changes, and add "location permission prompt and native HTTP" to the Stage 5 list. Run the stage 4 e2e variant with `Capacitor` absent, not only with the engine swapped.
Already covered?: No. Stage 5 covers saved-data origin only.

F6. Stage 5's checklist omits two Android items that the .NET 11 toolchain makes automatic: the default target is API 37, and Blazor and MAUI hybrid views are supported only on the latest WebView.
Severity: MINOR   Confidence: HIGH   Lens: R1
Claim: A .NET 11 Android project targets API 37 by default, which turns on Android 17's mandatory local-network permission for apps that target 37, and the current app's phone-to-desktop Wi-Fi link (D36) needs that permission; separately, the current app declares a WebView floor of Chrome 108 and the MAUI shell has no equivalent guard and only latest-WebView support.
Evidence:
- Target 37: the .NET for Android 11 manifest's `WorkloadDependencies.json` (`android-t2/disc/`) lists `Android SDK Platform 37.0` and `build-tools;37.0.0` as non-optional; Microsoft.Maui.dll 11.0.0 ships `lib/net11.0-android37.0`; the current app is `targetSdkVersion = 36` (`android/variables.gradle`).
- Android doc "Local network permission" (read 2026-11-12): "Starting in Android 17 (API level 37), local network protections are enforced for apps targeting Android 17 or higher"; "Making an outgoing TCP connection: yes"; "Traffic originating from Android Webviews that require local network access will inherit permission state from the host app"; apps targeting 36 or lower "receive an implicit permission grant". Android 17 behavior-changes page repeats it.
- WebView floor: `capacitor.config.ts` `minWebViewVersion: 108` shows an "update the WebView" message; Learn Blazor supported platforms (updated 2026-11-04): "we test on and support the latest platform Web View control versions: ... Chrome on Android".
Why it matters: A faithful MAUI replacement either keeps targetSdk 36 (set explicitly in the manifest) or adds a runtime-permission flow to a feature the page already ships. Stage 5 is meant to list these.
Plan change: Add two rows to Stage 5: "target SDK (37 default vs the app's 36): desktop link needs ACCESS_LOCAL_NETWORK or an explicit targetSdkVersion 36 in the manifest" and "WebView floor: what the shell does on a WebView older than the app's Chrome 108 floor". Record the 16 KB result too (see "found sound").
Already covered?: Partly. Stage 5 lists the API 24 floor but neither of these.

## Checked and found sound
- Minimum Android: plan "API 24 floor" matches Learn (.NET MAUI 11 what's new, ms.date 2026-09-10): "minimum supported Android API level has been raised from 21 (Lollipop) to 24 (Nougat)". The current app's `minSdkVersion = 24` (`android/variables.gradle`), so no floor regression.
- CoreCLR default and NativeAOT experimental: Learn (2026-09-10) "CoreCLR as the default runtime for standard apps. NativeAOT is also available as an experimental, opt-in publishing alternative"; Microsoft devblog 2026-07-14 "Starting with .NET 11 Preview 6, CoreCLR is the only runtime for .NET MAUI mobile apps ... Android is within 10 percent of Mono on startup and app size" (no absolute numbers, nothing on memory).
- 16 KB page size: the .NET 11 CoreCLR runtime pack and Android runtime libraries are 16 KB aligned. I ran `readelf -lW` and a RELRO check on `libcoreclr.so`, `libclrjit.so`, `libSystem.Native.so`, `libSystem.Globalization.Native.so`, `libSystem.IO.Compression.Native.so`, `libSystem.Security.Cryptography.Native.Android.so` (all in `microsoft.netcore.app.runtime.android-arm64` 11.0.0), plus `libnet-android.release.so` and `libarchive-dso-stub.so` (CoreCLR.37 arm64 pack): every LOAD segment has `Align 0x4000` and no RELRO end falls inside writable data. Google's rule (developer.android.com/guide/practices/page-sizes): apps targeting 15 and higher "must support 16 KB memory page sizes on 64-bit devices on Google Play. Starting February 1, 2027, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates." The app today is sideloaded (README "debug APK", `scripts/build-android-apk.sh`), so the deadline does not bind the prototype; it would bind a Play release. APK-level zip alignment could not be checked (no APK).
- Linux gap and platform list: Learn supported-platforms (2026-09-08) lists Android 7.0, iOS, Mac Catalyst and Windows 10/11; Linux absent. Artifact sentence "Linux is not a MAUI platform" is accurate.
- Blazor WebAssembly on .NET 11: Microsoft devblog 2026-07-14 "Blazor WebAssembly still uses Mono"; the web worker template exists (`blazorwebworker`, renamed in the .NET 11 release notes). "No real threads" is a simplification (an experimental opt-in `WasmEnableThreads` exists and needs cross-origin isolation); I found no .NET 11 source saying it is supported for Blazor, so the artifact's sentence is acceptable.
- Blazor Server requires a live server connection: not disputed by any source I read.
- Workload install on Linux x64: `dotnet workload install maui-android` completed in the T2 log (EXIT 0) and installed the CoreCLR, Mono and NativeAOT 37 packs; `dotnet-maui-doctor` points (maui-android only, explicit `--version`) are consistent with that. The second install (adding `android --version`) was redundant and is what ran out of disk.
- Origin: HybridWebView is served from a fixed `https://0.0.0.1/` (main branch: `AppOrigin = $"{AppHostScheme}://{AppHostAddress}/"`, `AppHostAddress = "0.0.0.1"`; the 11.0.0 `Microsoft.Maui.dll` contains the UTF-16 string `0.0.0.1`) and BlazorWebView from `https://0.0.0.0/` (`BlazorWebView.Maui.dll` 11.0.0 contains `0.0.0.0`); neither is `https://localhost`, so plan Stage 5's premise ("a MAUI shell serves from a different origin") is right and there is no setting to change it that I found.
- The artifact's "my understanding is that it is a message channel, not shared memory": accurate for both routes (strings via `PostWebMessage`; JS to .NET via `window.external.sendMessage` / an intercepted `fetch`).
- Chromium Local Network Access for WebSockets (Chrome M147 target) is "unsupported on WebView" (blink-dev Intent to Ship, 2026-02-19), so Chrome's own prompt does not gate a WebView loopback socket; the gating that can apply is Android's, see F2 and F6.

## Could not check
- Nothing ran on a phone, and no APK exists, so: real cost of (a) to (e), WebView behaviour for `ws://127.0.0.1` from `https://0.0.0.1` under `MIXED_CONTENT_NEVER_ALLOW`, whether the Android 17 local-network permission applies to 127.0.0.1, APK-level 16 KB zip alignment, Web Worker, WebGL and `requestAnimationFrame` behaviour inside BlazorWebView or HybridWebView (I found no report of a problem and no positive evidence either).
- Chromium's read chunk size for `shouldInterceptRequest` streams (chromium.googlesource.com returned 404 to the fetch tool), so route (d)'s throughput for 16 MB is unknown and is exactly what Stage 2 should measure.
- Whether `BlazorWebView` exposes `WebResourceRequested` in the public API the same way `HybridWebView` does (the 11.0.0 DLL contains the names; I did not read the public surface).
- Whether a Release APK builds in this container (needs the crossgen2 pack and more disk than is free).
- dotnet/maui and dotnet/android issue trackers: `gh` access to those repositories is not enabled for this session, so I searched the web and read raw source instead of listing open issues; my "no issue found on large payloads" is a web-search result, not a tracker query.
