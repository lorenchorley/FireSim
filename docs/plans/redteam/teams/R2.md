# Red team R2 (METHOD): can a gate pass when B is bad, or stop when B is good?

F1. Stage 1 profiles and gates the wrong tier: the phone's default run is the 3-D Standard tier, where the fire kernel the plan expects to port is 12 to 17 % of the time.
Severity: BLOCKER   Confidence: HIGH   Lens: R2
Claim: The default performance mode ("auto") builds the Standard tier and keeps it unless the 3-D air is "hopeless", which it is not on the one phone measured. Stage 1 profiles only the fast tier (Battery mode) and gates on a kernel's speed-up, not the run's. So Gate 1 can pass on a fire-spread kernel whose largest possible effect on a default phone run is about 1.2x (Amdahl), and Stage 3 may skip the atmosphere entirely ("defer the atmosphere port").
Evidence:
- `src/ui/settings.ts:195-203` sets `default: return { maxEmbers: 3000, ..., tier: 'auto' }`. The fast tier is only `case 'battery'`.
- `src/sim/simulation.ts:430` has `const buildTier = this.tierReq === 'auto' ? 'standard' : this.tierReq`.
- `src/sim/params.ts:44-48` says: "The 3-D air is kept when T_pred <= budget (the cut-off is about 198 ms per air step for a 6 h run, 4.8 times the one phone measured so far)".
- Plan 15e (`docs/plans/air-slice-wind-detail-honest-speed.md`, "Where the time goes") says: "Fast tier at 30 m: fire 58 % ... The 3-D tiers: air 63 % (Standard) and 82 % (High)". Line 951 says: "the Standard (3-D) tier spends 64 to 70 % in the air and 12 to 17 % in the fire".
- Even within the fast tier, `3a-reference.md` shows that advance is 1,050 ms of a 2,388 ms process (scenario build 514 ms and moisture spin-up 734 ms are not in any kernel).
Why it matters: A Gate 1 pass would tell the owner that B makes the phone faster when the default user's run would barely change. A 2x fire kernel gives 1/(0.85 + 0.15/2), about 1.08x, on Standard.
Plan change: Profile the tier the owner's phone actually runs (read the auto-tune event in Debug statistics). Port and benchmark the hottest kernel of that tier, which is almost certainly the air step on Standard. Gate on the whole `advance` time, extrapolated with the profile shares, not on kernel time. State the Amdahl ceiling next to every kernel ratio. Stage 3 must not defer the atmosphere if Standard is the phone's tier.
Already covered?: No. Section 3 says "the profile decides", but the profile is fixed to the "Katoomba 6 km fast-tier scenario".

F2. Gate 1's phone bar ("under 2.0x on the phone") has no phone TypeScript measurement to divide by.
Severity: BLOCKER   Confidence: HIGH   Lens: R2
Claim: The plan's only phone deliverable for Stage 1 is a C# benchmark app (K1: "a minimal Android benchmark app for the phone"), and the TypeScript side is "a Node harness". Node does not run on the phone. The phone ratio would therefore be phone C# against desktop Node, or would not exist. The phone's TypeScript also runs on a different V8 (the Chrome WebView's, in a worker) than Node v22's.
Evidence: Plan section 3, Stage 1 row and detail. Section 4, K1 row. Section 9, microbenchmarking row: "The TypeScript side stays a Node harness". The app already ships a phone TypeScript baseline: `src/ui/speedTestKernels.ts:1-12` describes 'K1 "air stencil": a 45 x 45 x 20 Float32 grid ... (the two things the air step spends its time on)' that is "FROZEN" with a pinned checksum. `src/ui/speedTest.ts:1-5` says it runs "off the main thread", against `SPEED_TEST_REFERENCE = { stencilMcellsPerS: 53.5, ... }` (line 38).
Why it matters: Gate 1 on the phone, the gate that decides whether B has any phone value, cannot be computed honestly as written. Whatever number appears will compare two different machines or two different JavaScript engines.
Plan change: Add a Stage 1 phone step. Port the frozen K1 stencil bit-exactly to C#; it is about 100 lines, and the checksum in `speedTest.kernels.test.ts` proves equivalence. Run it in the MAUI benchmark app right after the app's own speed test on the same phone, in the same thermal state. For the real kernel, add the TypeScript kernel to a WebView worker page inside the same MAUI test app, so both sides run on one device. This is also the cheapest experiment missing from the plan (see the end of this report).
Already covered?: No.

F3. Stage 1 can pass on a kernel that Stage 3 is not allowed to use: no output check, no thread-count rule, and the spread step draws from the random stream inside its loop.
Severity: MAJOR   Confidence: HIGH   Lens: R2
Claim: Stage 1 compares timings "on identical inputs" but never requires identical outputs. It also does not apply rule 4 (bit-identical on 1, 2, 4 and 8 threads) to the benchmarked `Parallel.For` form. The spread step consumes the fire random stream per cell, in band order: VLS periods, breach draws and debris Poisson draws. Revision 2 requires that order to be reproduced exactly. A parallel kernel that reorders or skips those draws, or drops side outputs, can post a large speed-up that the faithful Stage 3 port loses.
Evidence:
- `src/fire/spread/FireSpreadModel.ts:33-34`: "Determinism: fixed iteration orders (sorted band, list order), all randomness from the fire RNG stream (VLS periods, breach draws, debris)".
- `:1504` is `const breached = this.rng.next() < p;` and `:1954` is `const nItems = this.rng.poisson(lambda);`, the latter inside `for (let a = 0; a < this.activeCount; a++)`.
- Plan section 1 rule 4. Plan section 10: "The slice ports the TypeScript random generator and its draw order exactly".
Why it matters: Gate 1 passes and Gate 3 later fails, or Gate 3 passes with a slower serial kernel. In both cases the owner is told about a speed-up that the shippable code does not have.
Plan change: A Stage 1 kernel counts only if:
- its output arrays and random-generator state after N steps equal the TypeScript's on the fixture (an exact checksum, or the Stage 3 bars for floats);
- its output is identical on 1, 2, 4 and 8 threads;
- its timing includes the random draws in their original order.
Report the serial-fraction cost of keeping the draw order.
Already covered?: Partly. Rule 4 exists for Stage 3, and revision 2 fixes the draw order, but neither is applied to the Stage 1 benchmark that the gate reads.

F4. Gate 2's rates are not derived from what the phone produces: 16 MB is a desktop-only 10 m picture, and the real rate scales with solver speed and display step.
Severity: MAJOR   Confidence: HIGH (sizes and settings) / MEDIUM (inferred 9 km size)   Lens: R2
Claim: On a phone, pictures are 30 m at 3, 6 or 9 km: about 0.7 MB, 2.2 MB and, by inference from the cell count, about 5 MB. 16 MB is the 10 m picture of Desktop detail, which runs only on a desktop engine. 6.5 MB is the one-off scenario message, not a picture. The phone's picture rate is solver speed divided by display step, and every picture enters the history. A faster C# solver (a Gate 1 pass) therefore raises the rate Gate 2 must sustain beyond 4 per second. Example: at Max speed, a 6 km fast run at a 10 s step and 200x is 20 pictures/s, or 44 MB/s.
Evidence:
- `src/ui/setupModel.ts:37`: `EXTENTS_KM = [3, 6, 9]`.
- `3a-reference.md`: snap-60 is 680,064 B at 100x100 and 2,283,808 B at 200x200.
- Plan 15e: "one snapshot 2.3 MB at 30 m, 16 MB at 10 m". D35: "When the engine is the desktop, the person can choose finer cells (down to 10 m)".
- `src/ui/settings.ts:56`: `TIME_STEPS = [10, 30, 60, 120, 300, 600]`, default 60 (line 72).
- `src/ui/screens/sim/speedModel.ts:4`: presets up to 3600, plus Max.
- `src/ui/setupModel.ts:306`: `snapshotInterval: settings.timeStep`.
- Plan section 3, Stage 2: "2.2 MB pictures at 4 per second and 16 MB pictures at 1 per second".
Why it matters: Gate 2 can stop B on the phone because of a 16 MB case the phone never sends. It can also pass B at 4 per second while a faster solver needs several times that, which would make the transport, not the solver, set the phone's speed. That would erase the Gate 1 gain without anyone noticing, because the gates are read separately.
Plan change: Derive the Stage 2 rates from Stage 1's measured phone speed: rate = (sim s per wall s at Max) / (10 s and 60 s display steps), at 0.7, 2.2 and about 5 MB. Move 16 MB to the desktop-host check (Stage 4). Report one combined number for Gates 1 and 2: end-to-end simulated seconds per wall second on the phone, with pictures delivered into the history, against today's APK on the same phone.
Already covered?: No. Section 4 says Gates 1 and 2 are "decided together", but no rate is coupled.

F5. Gate 2 can stop B while a binary route exists: two of the three transports are string-only on Android, and the native ArrayBuffer channel is not tested.
Severity: MAJOR   Confidence: HIGH   Lens: R2
Claim:
- BlazorWebView on Android sends every message as a string. A maintainer says data goes as base64.
- HybridWebView's raw message API takes a string.
- AndroidX WebKit supports posting a `byte[]` as an ArrayBuffer to the page (`WebMessageCompat`, `WebViewCompat.postWebMessage`, `JavaScriptReplyProxy`). This avoids base64 and opens no loopback socket. The plan's three transports omit it.
If (a) and (b) fail on base64 cost and (c) fails on socket or flow-control cost, Gate 2 says "phone C# solver stops" without testing the obvious binary path.
Evidence:
- https://raw.githubusercontent.com/dotnet/maui/main/src/BlazorWebView/src/Maui/Android/AndroidWebKitWebViewManager.cs (main branch, fetched 2026-11-12): `protected override void SendMessage(string message) { _webview.PostWebMessage(new WebMessage(message), AndroidAppOriginUri); }`.
- https://github.com/dotnet/aspnetcore/issues/43867 (2022, closed 2025-09-06 as a duplicate of #62312). javiercn: "everything between the .NET side and the Webview2 needs to be marshalled as a string ... converting it to a base64 string".
- https://source.dot.net HybridWebView.cs: `public void SendRawMessage(string rawMessage)`.
- https://developer.android.com/reference/androidx/webkit/WebMessageCompat (current): a constructor taking `byte[]` for an ArrayBuffer payload, gated by `WEB_MESSAGE_ARRAY_BUFFER`. The JavaScriptReplyProxy page warns that large buffers can cause out-of-memory crashes on low-end devices.
- dotnet/maui#28667, "MAUI Blazor Hybrid has worse render performance": still open, milestone ".NET 12 Planning" (set 2026-11-01).
Why it matters: A false STOP. Section 7 would retire the phone C# solver because of transport choices, not because of anything inherent to B.
Plan change: Add transport (d), the native Android WebView `postWebMessage` with an ArrayBuffer through a `MessagePort`, reached from MAUI's platform handler. Record whether the WebView version supports `WEB_MESSAGE_ARRAY_BUFFER`. Gate 2 stops only if (d) also fails.
Already covered?: No. Section 3, Stage 2 lists only (a), (b) and (c).

F6. The 30-seed ensemble bar (mean burnt area within 12 %) cannot reliably fail: a port with a 10 % systematic bias passes about two times in three.
Severity: MAJOR   Confidence: HIGH (arithmetic) / MEDIUM (cv)   Lens: R2
Claim: With cv between 19 and 27 % per run, the difference of two independent 30-seed means has a standard error of 4.9 to 7.0 %. Pass probabilities for a given true bias:

| true bias | P(pass), cv 19 % | P(pass), cv 27 % |
|---|---|---|
| 0 % | 99 % | 91 % |
| 10 % | 66 % | 61 % |
| 15 % | 27 % | 33 % |

The cv itself comes from 6 and 4 runs. The 95 % interval on the standard deviation for n = 6 is 0.62 to 2.45 times, so the cv could be 12 to 47 %. At 40 %, even a correct port fails 25 % of the time. The bar also checks only the mean area: spot direction, spot count and arrival maps are unchecked.
Evidence: `3a-tier-difference.md` gives the cv per tier, and the plan section 10 table gives the bar. `node` computation (normal approximation): "cv 19% se 4.9%: bias 10%: P(pass)=66% ... cv 27% se 7.0%: bias 10%: P(pass)=61%"; chi-square factors for n = 6: 0.62 and 2.45.
Why it matters: If the exact random stream cannot be reproduced, which is the plan's own fallback, Gate 3 becomes a near-certain pass for a biased port. Section 7 then reads "All pass: B is technically feasible".
Plan change: Replace it with an equivalence test (TOST) at a margin the owner chooses. Size the runs for 80 % power: about 57 runs per arm at cv 19 % for a 10 % margin, about 114 at cv 27 %. Each TypeScript run takes about 1.3 s; C# runs are expected to be similar. Run the 30-seed TypeScript ensemble first to measure the cv. Add distribution checks: a two-sample KS test on burnt area, spot-fire count and ember-landing distance, and the per-cell burn probability map.
Already covered?: No. Section 10 says only that the 30-seed ensembles are "Still to run".

F7. Gate 3 can pass on seed 11, which exercises no ember code. The plan still names seed 11 as the fixture and never makes seeds 12 and 13 mandatory.
Severity: MAJOR   Confidence: HIGH   Lens: R2
Claim: Seed 11 at 3 km produces no effective spot fire. Its burnt area equals the no-embers run (56.7 ha), so a tight-bar pass and a thread-count pass on seed 11 test only the fire spread. The 3a report says to use seed 13 or 12. The plan's Stage 3 text and revision 2 bars do not adopt this, and revision 2 says only "same tier, same seed".
Evidence: `3a-tier-difference.md`: "Seed 11 ... starts no effective spot fire ... a per-seed check of the embers on seed 11 alone proves nothing about the ember code: use seed 13 (95.6 ha, many spots) or seed 12". Plan section 3, 3a: "seed 11". Section 10, item 2 notes it but sets no rule.
Why it matters: The ember model is 2,271 lines and the main source of divergence, yet a Gate 3 pass could leave it unverified. The thread-count test on seed 11 would also miss nondeterminism in parallel ember code.
Plan change: The Gate 3 tight bar and the thread-count test must pass on seeds 12, 13 and 14 at 900 s and 1800 s, with seed 11 as an extra. Seed 13 is required for the thread-count test.
Already covered?: Partly. Section 10, item 2 records the fact, but no gate uses it.

F8. Gate 1 compares all-core C# with single-thread TypeScript, measured with different harnesses, and has no phone measurement protocol. A pass may reflect parallelism the TypeScript could also have, and a fail may reflect a naive port; section 7 reads both as final.
Severity: MAJOR   Confidence: MEDIUM   Lens: R2
Claim:
- Plan 15e already estimates 1.8 to 2.0x for the fire on 4 cores with JavaScript workers and 1.9 to 2.6x for the air. A C# all-core ratio of 1.5 to 2.0 therefore does not separate "C# is faster" from "threads are faster", which TypeScript can also use.
- BenchmarkDotNet reports steady state (warm-up, Tier-1 with PGO, outlier handling) against an unspecified Node harness.
- The Gate 1 desktop bar is decided on 4 shared vCPUs that the plan itself labels "indicative".
- On the phone, BenchmarkDotNet's usual model of one generated process per benchmark does not apply, so the revision 1 rule cannot hold there.
- The plan states no thermal protocol (cold against sustained), no core-cluster control, and nothing on the "fixed partition" cost on heterogeneous cores, where equal chunks wait for the slowest cluster.
- A Gate 1 fail is read in section 7 as "No speed argument for B anywhere", based on one kernel, one agent run and one container.
Evidence:
- Plan 15e: "Amdahl upper bounds on 4 cores: the air alone 1.9x (Standard) and 2.6x (High); the fire alone 1.8 to 2.0x". `3a-reference.md` gives three runs of 1050, 1099 and 1206 ms (about 15 % spread).
- https://benchmarkdotnet.org/articles/configs/toolchains.html: "generates, builds and executes a new console app per every benchmark".
- https://source.android.com/docs/core/power/performance: "performance can vary dramatically as device temperature limits are reached".
- https://source.android.com/docs/core/perf/performance-hint-api: apps should not set CPU affinity because the best core type "varies by device model".
- https://devblogs.microsoft.com/dotnet/dotnet-maui-moves-to-coreclr-in-dotnet-11/ (2026-05-13): "CoreCLR brings tiered JIT compilation, ReadyToRun (R2R) precompilation, and Profile-Guided Optimization (PGO) to mobile". The phone therefore has tiering and warm-up behaviour that the desktop BenchmarkDotNet job does not reproduce.
Why it matters: Both wrong answers are possible. Gate 1 can pass on a ratio TypeScript workers could match under D34, or stop on a port no expert has tuned, with section 7 then closing B "anywhere".
Plan change:
- Report three ratios: C# 1-thread against TypeScript 1-thread (the language effect, which is B's own value), C# N-thread against C# 1-thread, and both against the 15e bound for TypeScript workers.
- Use the same statistic and the same warm-up on both sides; for example, time both from one outer driver with matching iteration counts.
- On the phone, use an in-process timer with a written protocol: Release build, 5 cold and 5 sustained runs after 10 minutes of load, the cluster frequency or `sustained performance mode` noted, median and spread.
- Test fixed-equal against dynamic partitioning; determinism needs fixed per-cell order and fixed reductions, not equal chunks.
- Rewrite the section 7 fail row as "no speed argument from this kernel as ported", and list the headroom not tried.
Already covered?: Partly. Rule 3 labels container numbers "indicative", and section 9 adopts BenchmarkDotNet, but neither addresses the mismatch in comparison or the phone protocol.

## The cheapest experiment the plan does not contain
Before any porting, open Debug statistics on the owner's phone with the current APK.
- Read the auto-tune event, which shows the chosen tier and the measured air-step time against the about 198 ms cut-off.
- Run the built-in speed test.
- Play a default 6 km run at 600x and at Max, and read worker duty and the computed against asked pace.

If the phone already keeps the Standard tier with headroom and keeps pace at the speeds the owner uses, a phone speed-up has little user value and Gate 1's phone question is moot. If it does not, the same readings give the phone baseline that F1, F2 and F4 need. Next step, about one agent hour: port the frozen K1 stencil to C# (the checksum proves equivalence) and run it beside the app's speed test on the same phone.

## Checked and found sound
- **Last-bit risk.** Revision 2's claim that last-bit math differences are not the risk holds: the 3a perturbation study saw 0 cells move at 1e-15 and a 1.2 ms maximum change at 1e-9.
- **Bit-exact generator.** A bit-exact generator is feasible. `src/core/rng.ts` is mulberry32 in `Math.imul` and `>>>` integer arithmetic, so it ports exactly to `uint` C#. Only `normal()` and `poisson()` go through `Math.log`, `cos` and `exp`, which matches the 3a evidence on last bits.
- **Separate streams.** The random streams are separate per subsystem (`simulation.ts:434-437`: embers, fire = seed+1, explain = seed+2, atmosphere = seed+3), so draw-order fidelity can be checked per stream.
- **Same-tier comparison.** Revision 2's rule to compare the same tier is correct: fast against standard is 34 % differ with a 204 s median.
- **Fixture determinism.** 31 hashes are identical across 3 processes, and the 0.8.0 anchor hashes are reproduced.
- **Container topology.** `lscpu` reports 4 vCPUs, 1 thread per core, KVM. Cumulative steal in `/proc/stat` was about 1.25 % at the time checked, and load average was 0.65. Steal is not the main noise source right now; other agents' load is.
- **Runtime.** The CoreCLR runtime for MAUI on Android in .NET 11 is correct: Mono was removed in Preview 6 (devblogs, 2026-07; startdebugging.net secondary).

- Whether V8 runs with reduced tiers (Lite or jitless) on low-memory phones. v8.dev describes Lite mode, but I found no statement that the Android WebView enables it automatically.
