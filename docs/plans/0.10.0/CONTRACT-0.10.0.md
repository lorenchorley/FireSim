## 1. What the owner decided (2026-11-08, "Then go for not started")

## 4. The work

### 4.1 Lanes H2 and Q: reconnect and shared sessions

**Today (0.8.0 and 0.9.0):** a session is one worker per socket; closing the socket ends it; the page's only recovery is *Continue on this device*, which restarts from time 0.

**Reconnect.** The host keeps a session alive for `--keep-minutes` (default 10, 0 = never keep) after its owner's socket drops without a goodbye, **paused** (a detached session computes nothing: ground rule 2, and it bounds memory and CPU). `welcome` carries `session: { id, resumeToken }` (128-bit random, never logged). A `hello` with `resume: { id, token }` and the pairing code reattaches the owner: the host replays what the page needs (the last snapshot and the last status and engine info, kept per session, small) and the session continues **paused** until the owner says play. The controller (`RemoteSimController`) retries by itself on an unexpected close (a short, bounded backoff, for a stated total window, never forever) and reports `reconnecting` and `restored` as link events the chip words ("Reconnecting to the desktop…", "Reconnected. The run is paused."); when the window passes, today's closed path (the chip with *Continue on this device*) applies unchanged. While reconnecting, commands are not queued silently: the controls say the link is down (Q decides the exact behaviour, bounded, and says it). A page that reloaded can resume too (the token is kept for the page load only in memory and in `sessionStorage`, never in `localStorage`) and gets the latest state with **"earlier history is not kept"** said. A gap in a page's history while the link was down is said, not hidden.

**Shared sessions.** The owner can share the run read-only: a *Share* control on the desktop chip's sheet creates a share code (8 characters, same alphabet, valid for that session only, revocable); the host lists shared sessions to a paired page (`list` after `welcome`, only label, age, viewers and whether it is running: no scenario data); a viewer joins one with the share code. Viewers get every engine message the owner gets, replayed for a late joiner (the session's init: scenario, options and the ordered command log kept in memory for that purpose, bounded and said, then the last snapshot), then live; **a viewer cannot command the engine** (the host refuses and closes, not just the page); a viewer page shows the run read-only (controls for the run, edits and tools are disabled or hidden, a plain "Watching a run on the desktop (read-only)" line says so), builds its own history from what it receives and may scrub that. Limits: `--max-viewers` per session (default 8), per-viewer flow control that **never blocks the owner or the engine** (a slow viewer skips to the latest snapshot and the page says it skipped), the owner ending the session closes viewers with a sentence, the share code is never in a URL path or log. Q may deliver a reduced viewer (fewer disabled controls) only if it says exactly what a viewer can still do wrongly and why.

Protocol: `protocol: 3` (the page and host refuse a mismatch with 0.9.0's `RemoteVersionError`). Tests: pure codec/registry tests, an in-process host with a fake socket for reconnect (the link cut at every step of the handshake and mid-snapshot), a real-host e2e for reconnect after a killed socket and for a viewer. The security review is part of the lane: a resume token, a share code and a viewer's refusal each get a test that shows what they refuse.

### 4.2 Lane C: a cloud server

The host on a machine on the open internet, behind TLS, for people who want a shared compute server. **It cannot be deployed or tested from this machine beyond a local self-signed certificate: say so.** Build: `--tls-cert FILE --tls-key FILE` (https and wss, Node's `https` and `ws`, tested with a throwaway self-signed certificate made by `openssl` in the test), `--allow-host NAME` (repeatable, for the public name in the `Host` allowlist), `--public` as the one switch that sets what an open-internet run needs and refuses to start without the rest (a code of at least 20 characters from `--code` or `--code-file`, TLS or an explicit `--behind-tls-proxy`, a stated `--max-sessions`, an idle limit `--idle-minutes` that ends sessions nobody has used), per-address connection limits, the existing wrong-code rate limit made global as well as per-address, a session CPU and wall-time cap option, a Dockerfile and a compose file (non-root user, a read-only root file system where Node allows, no new privileges, the build of `dist/` inside the image), a reverse-proxy example (Caddy or nginx with WebSocket upgrade), and a threat-model section in `desktop/README.md`: what an attacker can do with the endpoint (compute, memory, a scenario as hostile input to the solver), what the flags bound, what they do not. Also run the existing fuzzers against the scenario decoder on the host (random and truncated frames) and report. **The container recipe and the proxy examples are untested here: label them so in the README.**

### 4.3 Lane V: the validity work (15d; ideas 1, 2, 3, 10, 17, 19, 20, 21, 23)

Read `studies/simulation-validity/README.md` and plan 15d. Build, each with node tests (the slow ones under `SLOW=1` like the existing validation suite; a failing property is **reported, not fixed or hidden**):
1. **Properties that must hold** (metamorphic relations, ideas 1 and 17): a terrain and wind rotated by 90 degrees give the rotated result (exactly, on square grids; say the tolerance if floating-point order needs one), more wind never slows the head, more moisture never speeds it, a firebreak never raises the burnt area, a change at time t leaves earlier results unchanged, grid and step refinement converge within a stated band on the bundled sites' small domains; run over randomised synthetic terrains (seeded), recorded with seeds.
2. **Golden scenarios** (idea 3): a small fixed set (flat and uniform slope; a ridge; the Katoomba V20 preset at 6 km for 1 h; one with a wind change) whose summaries (burnt area at set times, head rate of spread, arrival-time percentiles, ember landing percentiles, the snapshot hash) are stored in `src/sim/validation/golden/*.json` with stated tolerances, compared by a test and regenerated only by `npm run golden:update` (a script that prints a diff and refuses to run in CI mode). A change in the golden values is a change in results (D23): the commit that changes them says why.
3. **Stress and fuzz** (idea 20): random terrains, weather and ignitions including extremes; no NaN, no negative area, no runaway growth, a burnt cell never un-burns; seeded and logged.
4. **The claims register** (idea 2) `docs/validity/claims.md` (and a machine-readable `src/sim/validation/claims.json`): every number and behaviour the app shows to a person (the cards, the speeds, the slopes, the "how sure" lines), with its source, the check that covers it (a test id or none), its known error, its status (checked, partly, unchecked, **known gap**), and a pass mark written down before the check runs (idea 10). A test checks that every claim's check id exists. Do not claim a check exists that does not.
5. **The per-release validation card** (idea 23) in *How sure are we?*: generated from the register and the golden run summaries into a small data file, shown as a card with plain words: how many properties and golden scenarios pass, the convergence summary from the 15e data (30 m against 10 m differ by tens of percent on Katoomba), and the known gaps in the owner's words ("not validated against recorded fires"). Lazy chunk, small; say its kB.
6. **How far the tiers differ on real terrain with a fire** (idea 21): Node runs of Fast, Standard and High on two bundled sites for a few hours (the harness of `studies/desktop-simulation/01-cost-vs-detail/scripts`), summaries stored (a small file under `studies/simulation-validity/`), the numbers in the register and the card. One realisation per row: say so.
7. **Reproducibility across engines** (idea 19): the snapshot hash of a golden scenario from Node against the same run in a browser worker (Chromium): an e2e that fails if they differ and says by how much; if they differ, record it as a finding and give the tolerance the goldens need.
8. **Not built because the data cannot be had here:** a grass-fire test against the 1986 Annaburroo experiments (idea 11), hindcasts (13) and peer comparison with ELMFIRE or FARSITE (18). Try to reach the sources once (the sandbox has a restricted proxy); if a dataset is reachable and its licence permits, say so and stop (the orchestrator decides); otherwise record in the register that it needs data. Never type in numbers from memory.

### 4.4 Lane X: does the complexity score predict where 30 m and finer results differ? (15c, next step)

Using `studies/adaptive-simulation-quality/` (the quality map) and `studies/desktop-simulation/01-cost-vs-detail/` (the convergence runs and scripts), run (Node, under the lock, seeded) the Katoomba 6 km standard scenario at 30 m and at 10 m (and 20 m) with the per-cell arrival time saved, on at least three bundled sites, and measure whether the complexity score of the quality map (and each of its five parts separately) predicts where the arrival time differs between the grids: rank correlation, the share of the difference that the top-20 % complex cells carry, and against random sets of equal size. **The score was a first definition, not tuned**: do not tune it on the same runs you score it on (hold one site out). Result: a study note with the figures, what it shows and does not (one realisation, NSW hill country, 10 m model derived from stereo imagery), and **a recommendation: build adaptive refinement, or not, and why**. If positive, add a design sketch (where the refined state lives so rewind and determinism hold: the checkpoints; where fine meets coarse); **do not change the solver**. The orchestrator tells the owner and decides what follows.

### 4.5 Lane B: the cliffs data path (15b)

Read plan 15b, 9d (H-look, rule 10) and `studies/cliff-from-photo/`. Build the **mechanism** and nothing that needs data nobody has: an optional per-site `cliffs.geojson` (lines or polygons, each with an optional bare-rock share, a rock style id, a profile hint and credit/`capturedOn`) read next to `vegetation.geojson`, validated by a pure loader with unit tests (malformed files are refused with a plain message, never a crash), applied **to the drawing only** (the H-look shader's rock share and style and the sharpening of the profile), with the Data sets Terrain card saying "hand-mapped for N cliffs" and the credit, and `public/demo/provenance.json` taking the file's source and licence. **Nothing the simulation reads may change (rule 10; H-sim stays blocked)**: a test shows snapshot hashes and slopes identical with and without an override. No file is added to `public/demo` (there is no data: say so; fixtures live under the tests). Also write the short guide for the person who will map a cliff (`docs/cliffs-data.md`: the format, what a photo can and cannot give, 15b's honesty rules). The photo-to-depth tooling (a 1.3 to 1.6 GB model run on a desktop) is **not** built: say why (models are not reachable here, the output is not measured geometry).
