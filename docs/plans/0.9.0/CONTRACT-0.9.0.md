# 0.9.0: the desktop detail setting, the Android app's desktop link, the loose ends of 0.8.0 (decisions D35 to D39)

Status: contract for the build lanes (written 2026-11-08 by the orchestrator, committed before the lanes start). Read with plan sections 4 (ground rules), 15e, 23 (0.8.0 as built, its limits in 23.4, the verifier's findings in 23.6) and `docs/plans/0.8.0/J-CONTRACT-desktop-host.md`, which still describes the host and the page's link; this file amends it where it says so.

## 1. What the owner decided (2026-11-08, "Go for all the decisions (desktop detail, app connection and js budget). Go for next steps. Then go for not started")

* **D35 Desktop detail setting: build it.** When the engine is the desktop, the person can choose finer cells (down to 10 m), a bigger ember cap, the High air and a larger history budget, **labelled "finer grid, results differ, not validated"** wherever a result is shown. Off by default; phone results and the 0.8.0 behaviour are unchanged when it is off.
* **D36 The Android app connects to a desktop host: build it, and loosen the app's cleartext and mixed-content settings for it.** The app has no host to ask, so the person types the desktop's address and the code. Opt-in, one connection, never automatic. It stays offline otherwise.
* **D37 The all-JavaScript budget is raised from 1000 to 1060 kB gzip** (the entry stays 195, CSS 135 and 25, demo data 36, the APK 33 MB). Raised by the orchestrator in the contract commit; nobody else touches `scripts/check-bundle.mjs`. Ask again before raising further. New code still loads lazily where it can.
* **D38 The loose ends of 0.8.0 are in 0.9.0** (section 4).
* **D39 Then the stretch goals and the not-started list go in 0.10.0** (not this file).

## 2. Rules that hold for every lane (plan section 4 and COMMON-090.md)

1. **Results never depend on speed, display or statistics (rule 1) and nothing degrades silently (rule 2).** The Desktop detail setting is chosen by the person, shown, and recorded with the run; with it off, snapshot hashes are byte-identical to 0.8.0's for the same scenario and seed (a test).
2. **Rule 6 (offline) is amended:** on the Android app the only network use added is the opt-in desktop link to the address the person typed. The I4 network audit must still pass for everything else; the audit's allowance is extended in the narrowest way and said in the report.
3. One solver (D34). No second implementation.
4. Honest labels (rule 4), 44 px targets, nothing pops up by itself, no `role=alert`, no toast, the voice of `src/ui/content.ts:1-5`.
5. **Security of the host does not get weaker.** Every new way in (an allowed origin, an address typed by the person) is opt-in on the host's command line, listed in `desktop/README.md`, and covered by a test that shows it refuses what it should.

## 4. The work

### 4.1 Lane K: the Desktop detail setting (D35)

Read first: plan 15e "Measured" (the cost, memory and convergence numbers: 10 m on 6 km is about 77 times real time, 1.2 to 1.9 GB, a snapshot of 16 to 39 MB; finer cells give different results by tens of percent), 15c, `src/scenario/params.ts` (the fire cell size, 30 m and the 20 m high detail up to 6 km), `src/sim/params.ts` (air tier, ember cap 2000/4000/4000), the history budget in `src/ui/session.ts` and `memoryModel.ts`, the estimator (`paceModel.ts`), the debug statistics, the Run card on Setup, and how the host and the remote controller hand a scenario to the engine.

What to build:
1. A **Desktop detail** choice on Setup, shown only when the engine is the desktop (and only when a link is open or the code box is, like the Engine row): *Standard* (today) and *Finer* (and, if the measurement supports a second step, *Finest*; the lane decides how many levels from the numbers, 20 m and 10 m are measured). A level sets: the fire cell size (a whole multiple of the 10 m terrain grid; extents and domain rules as the code requires), the ember cap, the air tier allowed (High allowed whatever the phone's Auto would pick; the tier is still the person's choice and shown), and nothing else.
2. **The label.** "Finer grid, results differ, not validated" (the owner's words; plain voice) on the run's label, in the statistics, in the model card (*How sure are we?*), in the exported run summary if there is one, and in the time-lapse/recording if it records the run's settings. A run records which detail it came from, in the scenario or the run info the way the other settings are, so rewind, "Continue on this device" (it restarts with the settings it had: say what the page does when the device cannot run the detail: it must say so and offer the standard detail, never silently lower it) and any saved record carry it.
3. **Memory and size, on both sides.** The host side: the frame cap and session memory bound (lane H owns the guard; K gives H the figures through the report). The page side: the history budget must not grow on a phone's page (a phone viewing a 10 m run gets 16 MB snapshots and must thin as it does today); on a desktop-class page it may grow (say the number and why). The page must be able to refuse a detail whose snapshots it cannot hold, with a sentence.
4. **The estimator** knows the desktop's speed: no phone speed test is used for a desktop run; the figures shown are the host's measured steps (the existing pace/estimate path, with the engine's `perf`), not a guess. Say what is measured.
5. **Determinism and rule 1/2 tests:** with the setting off the snapshot hashes equal 0.8.0's (use the existing determinism spec's scenario and a stored hash from the 0.8.0 tree); with it on, the same scenario and seed give the same hash twice, and the detail never changes after the start.
6. **Honest limits:** the setting says it is for the desktop; it is not offered when the engine is this device; the Katoomba 4 h burnt area differing between 30 m and 10 m (2,483 and 2,738 ha, embers off 1,002 and 1,520) is the example the Help text may use if it quotes numbers (say "one scenario").

Acceptance: unit tests for the pure model (levels to parameters, label words, memory refusal), `e2e/desktop-detail.spec.ts` against the stand-in host (the choice appears only with the desktop, the label shows, the label survives Continue on this device with the standard-detail offer), and one real-host run at the finer level on a small scenario (lane H's flags; report the wall time and the snapshot sizes).

### 4.2 Lane H: the host (D36 host side, D38)

1. **Less before the code.** `GET /__firesim/host` returns only `{ "app": "firesim-desktop-host", "protocol": 2, "requiresCode": true }`. Name, cores, Node version and session counts move into the `welcome` message (after the code). `detectHost()` returns `RemoteHostProbe | null` (`{app, protocol, requiresCode}`); `RemoteConnection.info` keeps the full `RemoteHostInfo` from the welcome. A page and a host of different protocol versions give a distinct `RemoteVersionError` with the two numbers (the page says "update the app or the host").
2. **Allowed origins for the app (D36).** `--allow-origin ORIGIN` (repeatable, an exact `scheme://host[:port]`) and `--allow-app` (shorthand for `https://localhost` and `capacitor://localhost`, the Android and iOS shells' origins). The handshake's Origin check accepts the host's own origin (as now), an origin on that list, or no Origin; `GET /__firesim/host` answers with `Access-Control-Allow-Origin` for a listed origin only (and the preflight), never `*`. The `Host` allowlist (421) stays; `--lan` is still needed for another device to reach the host. Tests: a listed origin is accepted, an unlisted one refused (1008/403 as now), a rebinding-style `Host` refused, with and without `--lan`.
3. **Memory bound.** A session's scenario and its typed arrays cost about 17 times the scenario message outside the JS heap (23.4). Add a guard: `--max-session-mib` (default from `os.totalmem()` and `--max-sessions`, say how), checked when the scenario arrives from its size and cell count; refused with a distinct engine error the page can word ("this scenario is too big for the desktop's free memory"); the frame cap and `--worker-heap-mib` stay. Use lane K's figures when they arrive (10 m over 9 km is 1.9 GB peak, 39 MB a snapshot); until then the 15e measurements in the plan.
4. **`--open` without the code in argv.** The host opens `http://localhost:PORT/__firesim/open?t=TOKEN` with a one-time token (valid 60 s, one use) that redirects to `/#code=CODE`; the code never appears in the launcher's arguments or the process list. Test the token's single use and expiry; the browser launch itself is injected in tests.
5. **IPv6 and rebinding.** `--bind ADDRESS` (default 127.0.0.1; `--lan` still means 0.0.0.0, `--lan6` or `--bind ::` for IPv6, as the lane judges simplest), bracketed IPv6 in the `Host` allowlist, tests on `[::1]`. A real-browser rebinding test with Chromium's `--host-resolver-rules` mapping a hostile name to 127.0.0.1 (the page on the hostile name must get 421 or a refused handshake).
6. **A throttled-link measurement.** A test helper (Node, TCP) that delays and limits a connection (about 20 Mbit/s and 30 ms, then 5 Mbit/s and 80 ms) between a client and the host, running a real snapshot stream (Katoomba 6 km at 30 m, and at 10 m if lane K's detail exists in the tree you have: if not, use a synthetic 16 MB frame stream): record the host's peak memory, the time to the first picture, the round trip under load, and whether the 16 MiB hold / 4 MiB release flow control keeps the host's memory bounded and the page responsive. Change the pair of numbers only if the measurement says so, and say what you measured. This is a measurement on one machine with a simulated link, not Wi-Fi: say so.
7. `desktop/README.md` documents every flag and the amendments; `engine`, `server` and `security` tests extended.

### 4.3 Lane P: the page (D36 page side, D38)

1. **The code box in the Android app and for a typed address.** In the Capacitor app (and in a browser only with the test seam `?desktopaddr=1`, never by default) the Engine row offers *Desktop (another computer)* with an **address** field (accepts `192.168.1.20`, `192.168.1.20:4300`, `http://…`, a bracketed IPv6 address, a name; default port 4300; rejects paths, credentials and anything that is not http or https) and the code box. A pure `parseDesktopAddress` with unit tests. The address (not the code) is remembered in the preferences; the code is never stored. The connection is made with `connectRemote({ base, code })`; `detectHost({ base })` runs first so the row can say "No desktop answered at that address, check that it is running with --lan and --allow-app" in plain words. The page is told by the build (Capacitor) not to run the same-origin detection (as now).
2. **The two-step label.** Before the code the row says *Desktop*; after the welcome it says *Desktop (NAME, N cores)* (the host no longer gives them earlier).
3. **Fallback gaps (23.4).** (a) A retry after a failed spare engine must not need the dead host: keep what the spare engine needs (its script as a blob or bytes, the warmed chunks) in memory or Cache Storage from the time the link opens, so *Continue on this device* works after the host is gone, and say in the report what is and is not kept and its size. (b) The Setup path: *Continue on this device* after the host died at start must still build (the chosen demo site's data is fetched when the Desktop engine is chosen and kept, bounded). (c) Warm the speed-test worker and the scenario/estimate chunk. (d) **The model card's planning text says "this phone"**: it follows the engine (this device, or the desktop). Every change is pinned by a test or an e2e on the stand-in host.
4. **Protocol 2.** Adapt to the host's info split and `RemoteVersionError` (a sentence, not a stack).
5. **e2e:** a cross-origin test: the app served by `vite preview` on one port, a real host (`--allow-origin http://localhost:PORT`, started as a child process as `e2e/desktop-real.spec.ts` does) on another, the page connecting by typed address and code with the seam; a wrong code, an unlisted origin and a host that is not there each give their sentence.

### 4.4 Lane A: the Android app (D36 app side)

Make the WebView page at `https://localhost` able to open `ws://` and fetch `http://` to a desktop on the local network, and nothing wider than that where Android lets you say so. Candidates to evaluate and choose with reasons: `android:networkSecurityConfig` with `cleartextTrafficPermitted` (Android cannot scope cleartext to a private IP range: say what it can scope, and that base-config cleartext is app-wide if that is what is needed), `android:usesCleartextTraffic`, Capacitor's `android.allowMixedContent` (the WebView's mixed-content mode for the page's `ws://`), whether `CapacitorHttp` (native fetch, enabled in `capacitor.config.ts`) already covers `http://` fetches and what it needs for cleartext, and `server.androidScheme` (do NOT change it: changing the scheme changes the page's origin and loses every saved site and run). Build the APK (`scripts/build-android-apk.sh` under the lock) and show with `aapt2 dump xmltree` the manifest and network config the APK carries; **you cannot run it on a device or emulator here: say so**, and put the exact phone check-list steps for the owner in "Docs notes". Say plainly what the loosening costs (what traffic the app would now accept), and keep it as narrow as Android allows.

### 4.5 Lane R: why a held view leaves the forest unfinished (D38)

Evidence (plan 23.x, the idle-stop investigation): with the idle limit at 3 s on the software GL, before a picture drawn by hand `vegetation.placing` was true (14 s after the last activity, `heldStill` true, `dirty` false, `vegPending` 0), and after `renderNow()` (which places the trees and builds the buffers in one go: `pump(Infinity)`) it was false; the canopy differed all over in that run, once in 15 and once in 20 repeats. `SceneView.frame` counts `placing` in `animating`, so the loop should keep drawing until the placement is done. Find out why it did not, in the app: instrument, reproduce (the throwaway diagnostic is in the 23.x text), explain. If it is a defect (a placement that waits for the next frame while the view holds still, or a flag set outside the loop without waking it), fix it with the smallest change that keeps rules 1 to 3 and the idle stop's meaning (a held view draws nothing, and any activity wakes it), with a test that failed before; if it is not a defect, say what it is and prove it. Do not change the spec `e2e/wind-motion.spec.ts` (lane T owns specs; its settling picture stays).

### 4.6 Lane T: the failures of the 0.8.0 gate that passed alone (D38)

Eight browser tests failed in the full run and passed alone, and two unit tests failed under load: `e2e/air-slice.spec.ts:888` ("412 x 915: Set start is above the pinned footer (bottom 753, footer 726)") and `:1428` ("with the scroll-padding of 52 px at the foot, every probe lands on its control", 844 x 390 with a recording), `e2e/air-tool.spec.ts:151` ("browser.newContext: Test ended"), `e2e/gallery-070.spec.ts:289` (the sheet did not say "paused to save battery" within 30 s), `e2e/layers.spec.ts:358` (at the farthest zoom of 844 x 390 "nothing is drawn: level 0", level 1 read), `e2e/pace.spec.ts:72` (the pace button not visible in 240 s), `e2e/wind-detail-render.spec.ts:332` (the hand-over "faded in" 0.5 not 1), `e2e/wind-glyphs.spec.ts:171` (4x CPU: the p95 of a slice 19.8 ms against 12), and `src/render/slice/sliceRecorder.perf.test.ts` (p95 1.82 against 1.5 ms), `src/render/wind/detailStreaks.alloc.test.ts` (2,282.8 bytes against 1,024). The full run loads the machine for 1.6 hours with two workers.
For each: reproduce under load (run it beside a busy machine: `taskset`/a CPU burner under the lock is acceptable, say how), find what it waits for or measures, and fix the cause. **A spec race is fixed in the spec** (wait for the state, not for a time; an animation's end; a layout that has settled). **A measurement that depends on the machine's load is made to measure something load-independent** (counts, a ratio to a calibration loop run in the same process, or an assertion on work done not on time) or, where that cannot be, kept as it is with its failure under load explained in the test's header: **never loosen a threshold to make it pass without a measurement that justifies the new number, never skip or delete a test.** If the cause is a real defect in the app, do not fix it in this lane: report it with the reproduction. Run each fixed test 5 times under load and report passes. Also confirm the gate would no longer regenerate the gallery's curated pictures when run in full (the gate script restores them with `git checkout -- docs/screenshots`; do not change that, report if a spec writes pictures outside `e2e/gallery*.spec.ts`).
