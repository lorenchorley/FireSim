**Which kernels use which maths.** `LevelSetCore` uses only + - * / and `sqrt`: no `FsMath` call, no shim, the bits are the TypeScript's own. `PyrogenicKernel` calls `FsMath.Sin` only to build its two sine tables (once per instance; `Math.PI*(p+1)*(i+0.5)/n` and the eigenvalue factor, with `4 * sin(..) ** 2` written as `4 * (s*s)`). With the default `FsMath` implementation (the fdlibm port) that is Node 22's own `Math.sin` (T1.3: 0 mismatches in 23.4 M calls on 15 functions), so the TypeScript's bits need no shim; the test asserts that the default implementation is in use, and the golden file holds the TypeScript's hashes of the tables (`sx`, `invNx`, `lamX`, `sy`, ...), which the C# tables equal in both windows (and in WebAssembly). The test-only shim would be needed only if the default became CoreMathSharp (its `sin` differs from Node's in the last bit on some arguments); it was not built, as nothing here needs it.

**Forms** (`KernelExec`): scalar (a literal port in the TypeScript's operation order); `Vector128<double>` (two cells per vector, every per-lane branch a lane mask; reductions scalar in a fixed order); fixed chunks run by `Parallel.For` with `MaxDegreeOfParallelism = threads`, scalar or vector body.
- **evaluate**: band position a reads only the field, its own and its neighbours' phi and its own coefficients, and writes only its own `out`, `r1`, `n1x`, `n1y`: independent; chunks of 256 band positions (a constant); the one reduction, the CFL maximum, is combined from per-chunk maxima in chunk order. **The lazy speed request is the exception**: the TypeScript calls `hooks.ensureSpeed(k)` in the middle of the loop and the fire model's hook draws random numbers. The vector and parallel forms therefore first run a **serial pass in band order** that makes the same decisions and calls the hook (so the draw order is the TypeScript's), then evaluate with no hook in the loop. This gives the TypeScript's bits provided the hook writes only cell k's own coefficients (the fire model's `prepareCell` does; the real hook's writes are what the fixtures replay).
- **reinit**: the bounding box (serial min/max); the crossing test and initial distance (rows are independent); **the fast sweeps are Gauss-Seidel**, so the order of updates is part of the result: a blocked wavefront (32x32 tiles, the tiles of one tile-anti-diagonal in parallel, each tile swept in the TypeScript's order) gives every cell the same neighbour values as the serial sweep (used only when the box has at least 16,384 cells: a rule about the data); write-back and band rebuild by row chunks with a per-chunk count, a prefix sum in chunk order and a parallel fill (the band stays in row-major order).
- **solve**: six phases (coarsen + forward x transform, y transform + eigenvalue division, inverse y, inverse x, coarse gradient, bilinear to the fire grid with the cap), each a function of a row range, one output row per chunk, a barrier between phases; every sum over rows stays inside one output row in ascending order.

## 3. Mutation checks (what the tests would notice)

T1.4a found that a float32 store hides double-rounding order differences. Each kernel has a seam (`IEvalOps`, `IPyroOps`, `IDistUpdate`: static abstract members of a struct type argument, specialised by the JIT, so no cost in the real path; the real kernel passes the literal implementation). A test passes a mutant with **one expression changed** through the same scalar code on the real frames; the controls (the literal implementation) must equal the golden bits, and a **harmless swap** (operands of single `+` and `*` exchanged: commutative) must change nothing, which shows that the tests do not cry wolf.

| mutant (kernel) | caught on | by which output | not caught by |
|---|---|---|---|
| `(pl+pr)+(pd+pu)-4p` instead of `((pl+pr)+pd)+pu-4p` (evaluate, the Laplacian) | 8 of 8 real frames | `out` (Float64 tendency) | r1, n1x, n1y, maxC (unchanged) |
| `nuH*(R*lap)` instead of `(nuH*R)*lap` (evaluate) | 7 of 8 | `out` | the 8th frame has no negative Laplacian (the branch is not taken); float32 outputs |
| the four one-sided squares summed in reverse order (evaluate) | 8 of 8 | `out` | float32 outputs |
| `Math.FusedMultiplyAdd` in the speed (what a contracting compiler would do) | 8 of 8 | `out` | float32 outputs |
| `c * (1/cn)` instead of `c / cn` (evaluate, the normal) | 8 of 8 | `out`, `maxC` | |
| `(|nx| + (|ny| + 4 nu))` in the CFL candidate (evaluate) | **1 of 8** | `maxC` only | seven frames (the maximum is usually reached by a cell where both orders round alike) |
| commutative swap of operands (evaluate) | 0 of 8 (as it must be) | | |
| rows of every accumulation summed in descending order (solve) | 2 of 2 real fields | `psi`, `gx`, `gy`, and `vp` | |
| `psi * (f / (lamX+lamY))` instead of `(psi*f)/(lamX+lamY)` (solve) | 2 of 2 | `psi`, `gx`, `gy` | **`up`, `vp`** (float32) |
| bilinear weights multiplied out (solve, the interpolation to the fire grid) | **0 of 2: not caught** | | the doubles differ in 13,947 of 40,000 fire cells (900 s; 13,875 late) but **after the float32 store in 0**: the store rounds the one-ulp difference away on every cell of both real fields |
| the sweep sum re-associated `0.5*(aa+(bb+sqrt))` (reinit) | 4 of 4 real frames with the Float64 distance; **0 of 4 with the float32 distance** | the double `dist` | the float32 `dist`, `phi` and the band derived from it |
| commutative swap (solve) | 0 of 2 (as it must be) | | |

So what the Float64 intermediates expose (`out`, `psi`, `gx`, `gy`, the wide `dist`) is guarded against operand-order slips; what is stored straight to float32 (`r1`, `n1x`, `n1y`, `up`, `vp`, the float32 `dist`) is not, and the interpolation expression of the pyrogenic solve and the float32 `dist` are guarded only by being a literal port of the TypeScript's text (the structure: what is read and written, the order of the terms as written), proved by equal bits on the real frames. The `ReinitWide` and the `Gx`/`Gy`/`Psi` exposures exist for this reason; an equivalent exposure of u and v before their float32 store was not added (it would put a branch or an array into the kernel).

**Reading it.** (1) Scalar C# is 1.3 to 2.1 times Node on these kernels. (2) **`Vector128` is slower than scalar for `evaluate`** (1.5x slower at 900 s stage 1, 1.7x at 14,100 s): two doubles per vector, a band cell reads five phi values and up to eight float32 coefficients through gathers, and half of a band's cells (the burnt arrival cells, edge cells, all-zero cells) cannot pair; an untested explanation, but the measurement is plain, and "a kernel that does not vectorise is a valid result" (plan 9). The vector form of `evaluate` is correct (bit-equal) and not useful; the scalar form is the one to use. (3) `Vector128` helps `reinit` slightly at 900 s (0.89x of scalar's time; only the crossing-test row phase is vectorised, the Gauss-Seidel sweeps are dependency chains and stay scalar) and 7 % at 14,100 s, and it helps **the pyrogenic solve a lot (1.5 to 2.1 times scalar)**, which is dense row accumulation. (4) `Parallel.For` is overhead-bound at these sizes: evaluate stage 2 at 14,100 s gains 1.4x over scalar on four threads and stage 1 loses (its serial speed-request pass and the fork cost), `reinit` gains only where the wavefront runs (14,100 s: 1.08x; at 900 s the box is under the threshold for the wavefront but over the row-phase one, and the parallel form loses 29 %), the pyrogenic solve gains 1.5 to 1.8x from threads and **2.4 to 3.4x with threads and vectors together** (4.8x and 6.5x of the TypeScript). (5) The thread curve (stopwatch, `DOTNET_TieredCompilation=0`, one process, medians of 400 single operations; `threads.json` in the results file) is flat from 4 to 8 threads on 4 cores, as it must be; at 14,100 s pyrogenic solve scalar 2.45, parallel t=2 1.58, t=4 1.34, t=8 1.35 ms; `reinit` 2.71, 2.96, 2.26, 2.41; evaluate stage 2 0.076, 0.073, 0.040, 0.034.
**A JIT observation (indicative, one process per setting, stopwatch, `fast-diag`):** with default tiering the pyrogenic solve (scalar) takes 2.22 / 3.10 ms (900 s / 14,100 s) but 1.77 / 2.36 ms with `DOTNET_TieredPGO=0` or `DOTNET_TieredCompilation=0` (20 to 24 % faster), while `reinit` and `evaluate` are faster with default tiering (reinit 0.48 against 0.64 to 0.67 ms at 900 s; evaluate stage 1 0.019 against 0.020 ms at 900 s and 0.091 against 0.107 to 0.127 at 14,100 s). BenchmarkDotNet's own scalar pyro (2.16 / 3.35 ms) is on the default-tiering side. Whether the app should switch dynamic PGO off for the solve (project setting `TieredPGO`) is open; the cause (hot/cold block layout after PGO is the suspect) was not investigated. Per-process JIT settings are the app's to choose, so the benchmark numbers above are the default ones.

**Gate 1's fast-tier bar is 1.2x of the whole step over the best TypeScript arm.** At the 30-minute shares these three kernels cannot reach it however fast they get: they are 14.3 % of the step, so even at zero time the ceiling is 1.167x, and the measured projection is 1.07 to 1.10x. At the 4-hour shares the ceiling is 1.49x and the projection is 1.14 to 1.22x: **only the best form of each kernel with four threads (1.217x) reaches 1.2x, and by 1.4 %**. It is a kernel-only arithmetic projection (not a measurement of the step) against **one** TypeScript thread (T1.5 adds the `worker_threads` arms against which the parallel columns are worth less), on shared cores, with `Parallel.For` needing cores that a browser build does not have without cross-origin isolation (Fs.Wasm runs it on one thread). The embers (24 % at 30 minutes), kept serial in the faithful draw order, the wind for the fire (19 %, of which the solve is the 8.4 %), the picture (11 %) and the detectors (9 %) are not ported, so the plan's expectation holds: **the fast tier's whole-step gain from these kernels is small**; the gate stays `not run` (it is defined on the measured whole step, T6.4 and T6.6).

## 9. What the resume found and changed

1. **The TypeScript fixture loader read `int32` arrays as bytes** (`Fs.Bench/ts/air/lib.ts`, shared with T1.4a, which has no int32 arrays): the TypeScript timing harness replayed a frame with a garbage band, so `reinit` found no crossing cell, an empty band came out and its "0.19 ms" was the cost of a box with nothing to do; the first timing of the stopped builder would have shown C# three times *slower* than the TypeScript. Found by a probe that printed `bandCount 0`; fixed (`int32` → `Int32Array`); every TypeScript number in this report is from the fixed loader. The capture itself (in-memory arrays) and the golden hashes were right, as regenerating them showed.
2. **179 tests failed** in `BannedSymbolsTests` after the earlier work: the snippets there call `TensorPrimitives` to prove its ban, and the assembly reached the test project only through `Fs.Kernel`'s reference to `System.Numerics.Tensors`, which the work correctly removed. `Fs.Tests` now references the package itself (a test project; solver code still must not), lock file regenerated.
3. **The vector form of evaluate** called its scalar body once per unpaired cell with all of its set-up; it now sends runs of unpaired cells in one call and passes scalars (not ten vectors) to the pair body. It is still slower than scalar (section 5), which is the finding.
4. **The allocation tests were flaky** (2 failures in 7 full runs, one of them identified as `ScalarAndVectorFormsAllocateNothingPerCall`, 5,800 bytes in the vector form; suspected cause: tier-0 code); they now warm up for 600 ms. Eight filtered repeats and the final full run after the change were clean; that is evidence, not proof.
5. Added: mutation seams and tests (7 evaluate mutants, 4 solve mutants; the reinit one existed), the late window in the child processes, the WebAssembly timing (`BenchSetup`, `BenchOp`, `wasm-bench.mjs`, `wasm-merge.py`), `FastOps.cs` split out of the BenchmarkDotNet file (so `Fs.Wasm` can compile it), BenchmarkDotNet sessions merged (`fast-merge` takes a list), `finish-json.py`, a rewritten `measure.sh` that holds the lock for one step at a time, `ResultDocumentTests` now validates `1-fast-kernels.json`.
6. `Fs.Results.Tests` has a flaky test, `StoreContractTests.Concurrent_requests_for_the_same_key_hold_one_slot_between_them("table")` (failed in 2 of 5 runs here, passed in the other three; the folder is not part of this card): see the orchestrator note.

## 10. Things the orchestrator should know

1. **The three kernels cannot meet Gate 1's fast-tier bar at the 30-minute shares** (ceiling 1.167x, projection 1.07 to 1.10x) and reach it only narrowly at the 4-hour shares with four threads (1.217x of a ceiling of 1.49x). Whether Gate 1 is judged at a small or a large fire is the owner's (O-8): the bar needs the fire's size.
2. Vectorising `evaluate` does not pay; the pyrogenic solve is the one kernel that gains a lot from vectors and threads (3.9x and 6.5x of the TypeScript at 14,100 s).
3. Dynamic PGO makes the scalar pyrogenic solve about 25 % slower and the other two kernels faster (section 5); a JIT setting is a per-app choice.
4. Plan 10.4's rule against `TensorPrimitives` is now true of every folder of `Fs.Kernel` (the exemption is gone); `TOOLCHAIN.md` says so.
